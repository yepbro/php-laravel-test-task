# AGENT.md

## Проект

Стек: Laravel 13 / PHP 8.5, Inertia + Vue 3 + TypeScript, Tailwind 4, MySQL 8.4,
Redis-очередь (Horizon), Mailpit. Окружение — Laravel Sail (Docker).

Полное описание запуска и команд — `README.md`.
ТЗ: `plan/TZ-*.md`. Декомпозиция на задачи: `plan/tasks.md`.

## Цикл работы над задачами

Основная сессия выбирает очередную задачу из декомпозиции в `plan/tasks.md`,
делегирует её субагенту, верифицирует результат и вливает в `main` —
полный порядок и правила: раздел «Порядок выполнения задачи».
В каждый момент в цикле только одна задача: следующая не стартует, пока
текущая не влита и не закрыта. Задач не осталось — цикл завершён.

## Правила работы в цикле

Основная сессия управляет циклом; каждую задачу выполняет отдельный субагент.

- Вся работа — в основном рабочем дереве: ветка `t-NNN` создаётся checkout-ом
  в нём, все проверки гоняются одним Sail-стеком.
- Основная сессия вправе сама запускать проверки и при необходимости
  править код и документацию — но любые её доработки идут только через
  `git commit --amend` в коммит задачи, отдельный коммит не создаётся.
- Задача считается сделанной только после зелёного полного прогона
  в основном дереве и итогового коммита в `main`, ставящего статус
  `[сделано]` в `plan/tasks.md`.

### Порядок выполнения задачи

1. Основная сессия выбирает следующую независимую задачу в статусе
   `[новая]` (пропуская задачи, зависимые от ещё не выполненных), ставит ей
   `[в работе]` статусным коммитом в основной ветке, создаёт для задачи
   feature-ветку `t-NNN` и запускает субагента **в фоне** с моделью
   `zai-coding-plan/glm-5.3` с полным контекстом: текст задачи, ссылки
   на ТЗ, актуальное состояние репозитория, требования по проверкам.
   До уведомления о завершении основная сессия не трогает рабочее дерево.
2. Субагент выполняет внутренний цикл (реализация → тесты → документация)
   в ветке `t-NNN` и делает единственный коммит задачи (правила
   и формат — см. «Коммиты»). `plan/tasks.md` субагент **не трогает**:
   статусы меняет только основная сессия (пп. 1 и 5) — это делает статус
   честным («сделана» = «зелёные проверки в main»). Правки по ревью
   вносятся через `git commit --amend`. Субагент не пушит и не мержит.
   По завершении субагент возвращает полный отчёт: что сделано и какие
   решения приняты, результаты проверок, итоги ревью (замечания /
   исправления / отклонения / «не проводилось» — с причиной), хеш коммита.
3. После зелёных тестов субагент проводит код-ревью по схеме из раздела
   «Схема ревью» ниже, с доработкой в своей сессии: согласен с замечанием —
   фикс + amend + повторный полный прогон (`sail composer max`);
   не согласен — аргументированное обоснование и повторное ревью
   (до 3 раундов). Ревью обязательно;
   недоступность ревью-агента (лимиты, ошибки) — исключение: ревью
   не проводится, факт фиксируется в отчёте и теле коммита.
4. По уведомлению о завершении субагента основная сессия верифицирует
   результат: коммит на месте и ровно один, `git status` чистый, статус
   задачи — `[в работе]` в `plan/tasks.md`, отчёт полный (состав — п. 2),
   включая итоги ревью. Прогоняет `sail composer min` и точечные тесты
   (`sail artisan test --filter=…`). Найденные недочёты (код, документация)
   устраняются через `--amend` в коммит задачи — силами основной сессии
   или перезапуском субагента.
5. После верификации основная сессия вливает ветку задачи в `main`
   линейно — rebase + `--ff-only` — и прогоняет в основном рабочем дереве
   полный прогон всех проверок (`sail composer max`). Только при зелёном
   результате — объединяет статусный коммит старта и коммит задачи
   в один итоговый коммит (например, `git reset --soft` и новый коммит),
   которым ставит статус `[сделана]` в `plan/tasks.md` (статус ставит
   только основная сессия — см. п. 2); переписывание `main` для этого
   разрешено. После — удаление ветки задачи и итоговое резюме по задаче.
   Пуш — только по явному указанию (см. «Общие правила»). Красный
   прогон — откат `main` к состоянию
   до влития, правка на ветке `t-NNN` (amend-ом или перезапуском
   субагента) и повтор верификации с п. 4.

### Схема ревью

- Ревью делается через CLI-вызов `opencode run` с моделью
  `zai-coding-plan/glm-5.3#max`.
- Строго read-only: не меняет файлы репозитория, не делает коммиты
  и ветки. Единственная запись — отчёт `/tmp/opencode/review/NN-<slug>.md`.
- Отчёт: находки P0–P3 (P0 — безопасность/потеря данных/краш; P1 —
  значимый баг; P2 — качество кода; P3 — идеи), файл:строка, суть,
  предлагаемое исправление, уверенность (high/medium/low). Каждая находка
  проверяется по контексту: callers/консументы через grep по репозиторию
  до включения в отчёт; неподтверждённое — не находка.

## Всё выполняется внутри Sail-контейнеров

- Любые `php`, `artisan`, `composer`, `npm`, `npx` — только с префиксом `./vendor/bin/sail`
  (далее `sail`). Это гарантирует версии PHP/Node как в CI и доступ к MySQL/Redis.
- На хосте — `git`, работа с файлами и CLI-агенты (`opencode run`
  для ревью); любые `php`/`artisan`/`composer`/`npm` — только через
  `sail`. PHP на хосте не используется.
- Стек: `sail up -d` / `sail down`, статус — `sail ps`, логи — `sail logs -f`.
- Упал контейнер/healthcheck — сначала `sail ps` и логи, не чинить вслепую.

## Проверки

Полный прогон — финальный шаг задачи: после влития в `main`, перед
статусом `[сделана]` (см. «Порядок выполнения задачи», п. 5) —
`sail composer max` (стиль, типы, линт back + front, тесты Paratest).
Быстрая проверка в процессе — `sail composer min`.

- Бэкенд: `sail composer back` — Pint (автофикс) + PHPStan level 10.
- Фронтенд: `sail composer front` — Prettier + vue-tsc + Stylelint + hex-линт + ESLint.
- Тесты: `sail composer tests`; точечно — `sail artisan test --filter=…`.
- Перед коммитом субагента — зелёный полный прогон (`sail composer max`;
  в процессе — `sail composer min`).
- На верификации задачи основной сессией (до влития) — `sail composer min`
  и точечные тесты; полный прогон — после влития (см. выше).
- Команды с автофиксом (`pint`, `format`, `lint`) изменяют файлы — правки идут в коммит задачи.
- Упавшая проверка чинится в рамках той же задачи, а не откладывается.

## Код и конвенции

- Следовать структуре, именованию и стилю существующего кода; смотреть соседние файлы.
- `declare(strict_types=1)`, явные типы возврата, Laravel-way (Form Request для валидации,
  фабрики для моделей, `config()` вместо `env()` вне конфигов, очереди — через jobs).
- Тесты обязательны: новая/изменённая логика покрывается PHPUnit-тестами (happy path + ошибки + края) и API-тестами.
- Tailwind — только дизайн-токены; hex/rgb-литералы в классах запрещены (контролирует линт),
  allowlist не расширять.

## Документация

- Обновляется после успешных прогонов тестов, а не до.
- Что обновлять при изменении поведения, конфига, структуры проекта, миграций, Makefile: `README.md`, соответствующий файл в `docs/`.
- `AGENT.md` — обновляет основная сессия при необходимости, вне цикла
  задач; такие правки идут отдельным `docs:`-коммитом без номера задачи.
- `README.md` — точные команды запуска и адреса сервисов.
- `DECISIONS.md` — принятые решения, допущения вместо вопросов бизнесу, что осталось.
- Устаревшая документация — баг: править в рамках той же задачи.

## Коммиты

- Одна задача — один коммит (код, тесты, docs); `plan/tasks.md` субагент не трогает.
- Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`.
- Первая строка коммита задачи — называться как задача: `<тип>: <заголовок задачи из plan/tasks.md> (T-NNN)`. Пример: `chore: Поднять минимальный Laravel Sail + MySQL + Redis (T-002)`. Подставлять собственные краткие формулировки вместо заголовка задачи нельзя.
- Расшифровка — в теле коммита после пустой строки: одним параграфом или списком (что сделано, ключевые решения, результаты проверок).
- Не смешивать изменения, не относящиеся к задаче. Мусор (`var/`, `tmp/`, локальные конфиги) не коммитить.

## Общие правила

- **Не пушить без явного указания:** `git push` (в т.ч. `git push
  origin main` после вливаний) не выполняется, пока пользователь
  прямо не попросит об этом. Коммиты и вливания — локально, без пуша.
- Сомнения в трактовке ТЗ — решать по тексту ТЗ; принятое решение
  зафиксировать: кратко — в теле коммита, развёрнуто — в `DECISIONS.md`.
- Существующее поведение не ломать; изменения публичных контрактов (API,
  форматы, события) фиксируются в `DECISIONS.md` и соответствующем файле
  в `docs/`.

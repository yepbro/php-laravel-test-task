# План работ — MarketHub Orders Service

> Каждая задача имеет сквозной уникальный номер (`001`, `002`, …), заголовок, краткое описание, прямые ссылки на соответствующие разделы ТЗ, поле статуса и чек-лист подшагов. Все задачи изначально имеют статус `новая`.

> План реализации по `TZ-markethub-orders-service-v1.5.md` (v1.5). Выполнять задачи последовательно, не пропуская проверки и критерии готовности. Один пункт — один небольшой, проверяемый результат; по возможности один пункт соответствует одному коммиту.

## Правила работы

- [ ] Перед началом работ прочитать актуальное ТЗ, особенно §6–§8, §10–§13 и решения Q3/Q35. `plan/` — входные материалы, **не изменять**.

**Статусы задач:** `новая` → `в работе` → `сделано`. У каждой задачи есть отдельное поле статуса; чекбоксы внутри задачи отражают выполнение подшагов и не заменяют статус. Ставить `сделано` только после прохождения критерия готовности и связанных тестов.

- [ ] Работать в порядке этапов ниже: минимальная техническая основа → БД и генерация данных → скелет приложения → красные тесты → атомарная реализация → финальная приёмка.
- [ ] Для новой бизнес-функции сначала убедиться, что есть тест, который проверяет её поведение; при реализации конкретной задачи тест должен перейти из красного в зелёный.
- [ ] Не оставлять заглушки `TODO`, фиктивные ответы и `markTestSkipped()` в завершённых задачах.
- [ ] Суммы хранить и вычислять как decimal/string, не использовать `float`. Время сравнивать как моменты UTC, а не как строки.
- [ ] Код и комментарии для неочевидных решений, тесты и документацию обновлять в одном коммите.
- [ ] После каждого атомарного изменения запускать относящиеся к нему тесты; на этапах готовности — полный набор соответствующих проверок.
- [ ] Не добавлять зависимости или публичные эндпоинты, если это не требуется ТЗ. Не использовать авторизацию и не реализовывать реальную отправку почты.

## Definition of Done для каждой задачи

- [ ] Задача решает одну конкретную часть требований и не включает несвязанный рефакторинг.
- [ ] Есть тесты для нового поведения и регрессии затронутого поведения.
- [ ] Проверки не падают по причинам синтаксиса, загрузки приложения или окружения.
- [ ] Код соответствует Pint и Larastan level 10; подавления ошибок, baseline и `ignoreErrors` не добавляются.
- [ ] Документация обновлена в том же коммите, если меняются поведение, схема БД, переменные, API, запуск или админка.
- [ ] Коммит небольшой, осмысленный, с описанием на русском и Conventional Commits-префиксом (`feat`, `fix`, `test`, `docs`, `chore`, `refactor`).

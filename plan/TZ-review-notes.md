# Результат ревизии ТЗ MarketHub Orders Service и принятые решения

Дата: 26.10.2026.

## Какие источники сверены

- `TZ-markethub-orders-service.md` и предыдущая доработанная версия.
- PDF-экспорт истории Claude (`Claude.pdf`), в котором видны ответы пользователя на Q1–Q21 и подтверждение использования значений по умолчанию для Q22–Q34.
- Исходные файлы задания в публичном репозитории: `task/README.md`, `task/marketplace-webhooks.md`, `task/openapi.yaml`, пять JSON-событий, `signature-example.md`, `signature-example-body.json`, `send-event.php`.

Исходный каталог `task/` не изменялся; изменения касаются только ТЗ и рекомендаций.

## Подтверждённые ответы, отражённые в ТЗ

- В объём входят и ядро сервиса, и надёжность, и минимальная админка.
- Стек админки — Vue 3 + Inertia + Tailwind. Решение Q3 пересмотрено пользователем (27.10.2026): выбран гибрид — страницы на Inertia, данные заказов браузер запрашивает методами `openapi.yaml` (`GET /api/orders`, `GET /api/orders/{id}`); props — только вспомогательные данные.
- PHP 8.5, Laravel 13, MySQL 8.4, Redis 7, Inertia v3; Docker — стандартный Laravel Sail.
- PHPUnit, Pint, Larastan level 10; значение по умолчанию для CI — GitHub Actions.
- Секрет вебхука берётся из `MARKETPLACE_WEBHOOK_SECRET`; при пустом секрете проверка работает fail-closed.
- Неизвестный тип и неизвестное строковое значение статуса обрабатываются как `ignored` с HTTP 200 без применения состояния.
- Версия снимка — `(order.updated_at, event.created_at, event.id)`; даты сравниваются как моменты времени.
- Пользователь согласовал запрет откатов из `delivered` и `cancelled`. Дополнительно принято консервативное допущение Q35: запрещать и переходы между самими терминальными статусами (`delivered → cancelled` и `cancelled → delivered`); это не подтверждённое правило MarketHub, и его следует явно указать в `DECISIONS.md`.
- Снимки с потерянными статусами достраивают историю по `created_at`, `paid_at`, `cancelled_at`; сырые события хранятся 90 дней; API выдаёт даты UTC без долей секунды.
- По умолчанию включены outbox, очередь, догоняющая постановка, заданные тексты писем, политика дедупликации по трек-номеру для `shipped`, фильтр email точным совпадением и HTTP 422 для невалидных query-параметров.
- Все текстовые материалы должны быть на русском; подробности о языке технических идентификаторов и сообщений валидации оставлены как явно обозначенное допущение.
- В `.env.example` должны быть все переменные окружения; документацию требуется обновлять одновременно с кодом на протяжении разработки.

## Важные замечания, внесённые в ТЗ

1. **Q15 и Q35 не равнозначны.** Ответ «откаты из `delivered` и `cancelled` не допустимы» запрещает возврат к более ранним статусам, но не даёт отдельного ответа о `delivered → cancelled`. Теперь принято консервативное допущение Q35: любой переход из `delivered`/`cancelled` в другой статус запрещён. Это решение принято для реализации, но в `DECISIONS.md` должно быть обозначено именно как допущение, а не как подтверждённое правило MarketHub.
2. **Q3 пересмотрен: выбран гибрид (v1.5).** Админка на Inertia; данные заказов браузер получает запросами к методам `openapi.yaml`. Props — только вспомогательные данные. API проверяется независимыми контрактными тестами, админка дополнительно выступает его реальным клиентом; браузерные smoke-тесты (Playwright) обязательны.
3. **Не вводить требование о совпадении `event.type` со статусом без согласования.** Ответ по Q22 говорит о смене статуса в применённом снимке, а Q28 исключает письма-исправления при откатах. Поэтому текущая версия ТЗ не использует `type` как источник статуса и не добавляет отдельный запрет уведомлений только из-за типа события.
4. **Sail меняет способ «сборки на старте».** Код в Sail монтируется в контейнер, поэтому сборка фронта во время `docker build` не гарантирует работу с актуальными файлами. Подготовка ключа, миграции и сборка фронта выполняются идемпотентно при старте контейнера приложения; `queue`/`scheduler` ждут его готовности.
5. **Exactly-once для email недостижим в рамках обычной SMTP-отправки и транзакции БД.** При выбранном приоритете «не дублировать» зависший статус `sending` требует ручной диагностики и может привести к потере письма. ТЗ прямо отражает этот компромисс и не обещает одновременно отсутствие дублей и потерь.
6. **Гонка между проверкой статуса и отправкой.** Вебхук и отправка уведомления должны использовать одну блокировку по заказу; уведомление удерживает её на время проверки и SMTP-вызова. `dedupe_key` для `shipped` должен соответствовать тому же трек-номеру, что и тело письма.
7. **Неизвестный статус требует ограниченной проверки.** Для неизвестного строкового значения статуса нельзя валидировать весь заказ как известный enum и возвращать 422: согласованное поведение — сохранить событие как `ignored` и вернуть 200. При этом malformed JSON, отсутствующий конверт, отсутствующий обязательный `status` или неверный тип поля остаются 400/422.
8. **Примеры не покрывают весь протокол.** В каталоге нет самостоятельного примера `order.delivered`, неизвестного типа, неизвестного статуса и смены содержимого для повторного `event.id`. Для этих случаев нужны отдельные fixtures в `tests/Fixtures`; `task/` оставлять неизменённым.
9. **Не использовать `--ignore-platform-reqs` как замену проверке окружения.** Если одноразовый Composer-образ отличается от runtime Sail, после установки нужно выполнить проверки обычным Composer внутри реального окружения PHP 8.5 и убедиться, что расширения присутствуют.

## Текущий статус решений

| Пункт | Статус | Как реализовывать |
|---|---|---|
| Q3 — источник данных админки | **Решён: гибрид (пересмотр 27.10.2026)** | Inertia-оболочка + клиентские запросы к методам `openapi.yaml`; props — вспомогательные; зафиксировать историю выбора в `DECISIONS.md` |
| Q35 — переходы между терминальными статусами | **Допущение зафиксировано для реализации** | Запрещать любые переходы из `delivered`/`cancelled` в другой статус; разрешать обновление данных при сохранении того же статуса; явно отметить, что это не подтверждённое правило MarketHub |
| Q36 — TypeScript или JavaScript | Технический выбор по умолчанию | Использовать TypeScript (`<script setup lang="ts">`, `vue-tsc --noEmit`) |
| Q38 — язык идентификаторов и ошибок Laravel | Техническое допущение | Идентификаторы английские, человекочитаемые тексты и validation messages русские; зафиксировать в `DECISIONS.md` |

Q37 — не самостоятельное открытое бизнес-решение: это техническая адаптация автоматического запуска из Q9 к выбранному Sail.

## Критерий готовности

ТЗ готово к передаче разработчику или AI-агенту: Q3 закрыт гибридом (Inertia + данные из openapi-методов), Q35 зафиксирован как допущение, остальные несогласованные детали не выдаются за ответы пользователя, а требования сопоставлены с приёмочными сценариями и `DECISIONS.md`.

## 1. Цель и контекст

Интернет-магазин продаёт товары на своём сайте и через маркетплейс **MarketHub**. Маркетплейс сообщает об изменениях заказов вебхуками. Нужен сервис на Laravel, который:

1. принимает и проверяет вебхуки MarketHub, хранит **актуальное состояние** заказов, позиций и **историю смены статусов**;
2. отправляет покупателю **три вида писем** (оплачен / передан в доставку / отменён) так, что покупатель **не получает одно и то же письмо дважды** и **не получает писем, противоречащих текущему состоянию заказа**;
3. отдаёт заказы через **API для админки** строго по контракту `openapi.yaml`;
4. содержит минимальную **админку** на Inertia.js v3 + Vue 3 + Tailwind (в объёме работ, решение Q1);
5. сопровождается актуальной **документацией** (§12), которая поддерживается на протяжении всей разработки (§12.2).

Решение проверяют вручную и **автоматическими сценариями через HTTP**, поэтому формат вебхука и контракт API должны соблюдаться буквально. Оцениваются: корректность с учётом особенностей доставки вебхуков, бизнес-логика, качество и читаемость кода, владение Laravel, тесты, обоснованность решений (`DECISIONS.md`), история коммитов.

## 3. Результаты анализа материалов (ключевые выводы)

### 3.1. Проверки, выполненные над материалами

| Проверка | Результат |
|---|---|
| Подпись из `signature-example.md` пересчитана (секрет `whsec_test_5f1d8c2a9b`, timestamp `1792577149`, тело 765 байт) | **совпадает** с эталоном `4d4f2d50…cb163f7` |
| Что именно подписывается | `"{timestamp}." + сырые байты тела`. Тело — компактный JSON с **неэкранированной кириллицей** и экранированными кавычками `\"`; без перевода строки в конце |
| Перекодирование тела (`json_decode` → `json_encode`) | для обычных настроек даёт **другие байты** → подпись не сойдётся. В реальных событиях есть `/` в URL (`https://…`), которые `json_encode` по умолчанию экранирует. Подпись считать **только по `$request->getContent()`** |
| Примеры событий `order-*.json` | заканчиваются переводом строки; `send-event.php` подписывает файл «как есть» (с `\n`) → сервис обязан работать с любыми байтами, не нормализуя тело |
| Timestamp из примера | `1792577149` = 21.10.2026 10:05:49 UTC → при окне ±5 мин пример проходит проверку только при **замороженном времени в тестах** |
| Арифметика `total` во всех примерах | сходится: Σ(price×qty) + delivery − discount |
| Часовые пояса | все снимки в `+03:00`, **кроме** `order-shipped.json` (`updated_at: …+00:00`). Сравнивать надо **моменты времени**, а не строки/«настенное» время |
| Время внутри ULID в `id` событий | декодируется в октябрь **2024**, то есть не совпадает с `created_at` событий (2026) → **нельзя** использовать как источник времени |
| Один заказ `ord_7Q2KX9M4` | в примерах прошёл `created → updated → paid → shipped`; в `updated` состав изменён (2→3 футболки) и `total` вырос с `3619.50` до `4909.50` |
| `order-cancelled.json` | другой заказ `ord_3HV8PW2C`, **оплаченный** (`paid_at` заполнен) → пример для текста про возврат. Примера отмены **неоплаченного** заказа, `order.delivered` и ручного исправления статуса **нет** |

### 3.2. «Ловушки» протокола и их следствия

| # | Факт из документации | Следствие для реализации |
|---|---|---|
| T1 | Подпись по сырому телу, байт в байт | Считать HMAC по `getContent()`, сравнивать `hash_equals`, **до** любого парсинга |
| T2 | Окно ±5 минут по `X-Webhook-Timestamp` | Проверять модуль разницы (и «из будущего»); окно — в конфиге; в тестах `travelTo()` |
| T3 | Успех = 2xx **за ≤ 5 с**; тело ответа не анализируется | Синхронная часть быстрая (БД-транзакция), письма — **только через очередь** |
| T4 | Повтор — тот же `id`, **новые** timestamp и подпись; возможен повтор и после успеха | Идемпотентность по `event.id` (уникальный индекс), а не по подписи/timestamp |
| T5 | Порядок доставки не гарантируется | «Побеждает» снимок с более свежим `order.updated_at`, а не последний пришедший |
| T6 | Снимок — **полный** (`data.order`) | Состояние заказа перезаписывается снимком целиком (включая `shipment → null`, `paid_at → null`); тип события — не источник статуса |
| T7 | Ручные исправления статуса поддержкой (например, `shipped` отмечен по ошибке) | Статус может откатываться, поэтому нельзя реализовывать правило «только вперёд». По ответу Q15 откаты из `delivered` и `cancelled` запрещены. Для однозначной реализации любой переход из этих статусов в другой отклоняется; распространение запрета на переход между двумя терминальными статусами (`delivered ↔ cancelled`) — консервативное техническое допущение, описанное в §16.2 |
| T8 | `updated_at` с точностью до секунды | Возможна ничья по `updated_at` → детерминированный tie-break (§6.2) |
| T9 | Список типов событий и статусов расширяется без уведомления | Неизвестный тип → `ignored`/200 без требования `data.order`; неизвестный статус в известном событии → `ignored`/200 без изменения заказа. Отсутствующие или неверно типизированные обязательные поля остаются ошибкой 422 |
| T10 | В описании `order.updated` упомянут «адрес», в схеме заказа адреса нет | Игнорировать, хранить сырой снимок; вопрос маркетплейсу (Q16) |
| T11 | Время перехода в `shipped`/`delivered` отдельным полем не передаётся | `at` в истории берётся из `updated_at` снимка (см. пример `history` в OpenAPI: `shipped at = updated_at`) |
| T12 | В `openapi.yaml` `updated_at` — «время последнего изменения заказа» по данным маркетплейса | Не использовать Eloquent `created_at/updated_at` для этих полей: хранить `placed_at`, `source_updated_at` отдельно |

## 4. Границы проекта

**В объёме:** эндпоинт вебхуков; проверка подписи; идемпотентность; обработка неупорядоченных событий; хранение заказов/позиций/истории; журнал событий; очередь писем и дедупликация; API по OpenAPI; **минимальная админка** (список с фильтрами + карточка); окружение на **Laravel Sail** (+ воркер очереди, планировщик); тесты (PHPUnit); статический анализ (Larastan level 10) и Pint; `.env.example` со всеми переменными; `README.md`, `DECISIONS.md` и остальная документация из §12 **с обязательной поддержкой в актуальном состоянии** (§12.2).

**Вне объёма (явно по заданию):** авторизация API и админки; деплой; реальная отправка почты (достаточно Mailpit); вёрстка писем (простой текст).

PHP 8.5: проверить отсутствие deprecation-сообщений (в т.ч. `PDO::MYSQL_ATTR_*` в `config/database.php` — использовать `Pdo\Mysql::ATTR_*`), доступность расширения `redis` (запасной вариант — `predis`).

### 5.2. Docker: стандартный Laravel Sail (P0)

Решение Q7: стандартный Sail. Требование задания: приложение, БД, **воркер очереди**, Mailpit. Особенности Sail, которые влияют на ТЗ: код монтируется в контейнер `laravel.test` (в образ не копируется), веб-сервер — `php artisan serve` (nginx нет), `vendor/` появляется только после `composer install`, воркера и планировщика «из коробки» нет. Поэтому compose публикуется (`php artisan sail:publish`) и дорабатывается:

| Сервис | Образ / команда | Порт на хосте (Q8) |
|---|---|---|
| `laravel.test` | Sail runtime 8.5: приложение (`artisan serve`, supervisor), node/npm внутри; `PHP_CLI_SERVER_WORKERS ≥ 4` (проверить значение: параллельные вебхуки не должны блокировать друг друга); healthcheck по `/up` | `APP_PORT=80` |
| `queue` (добавить) | тот же образ Sail: `php artisan queue:work redis --tries=5 --max-time=3600`; `depends_on: laravel.test (healthy)` | — |
| `scheduler` (добавить) | тот же образ: `php artisan schedule:work` | — |
| `mysql` | `mysql:8.4`, healthcheck `mysqladmin ping` | `FORWARD_DB_PORT=3306` |
| `redis` | `redis:7-alpine`, healthcheck; порт на хосте публикуется через `FORWARD_REDIS_PORT` | `FORWARD_REDIS_PORT=6379` |
| `mailpit` | `axllent/mailpit`; SMTP 1025 внутри сети | UI: `FORWARD_MAILPIT_DASHBOARD_PORT=8025` |

**Старт «с нуля» (ответ Q9, техническая адаптация под Sail).** «Сборка фронта при сборке образа» с Sail невозможна (код монтируется), поэтому автоматические шаги выполняются при старте контейнера **идемпотентно**: опубликованный `start-container` (или `bin/setup`) делает ожидание MySQL → `key:generate` при пустом `APP_KEY` → `migrate --force` → `npm ci && npm run build`, если нет `public/build/manifest.json`. Выполняет их только `laravel.test` (флаг окружения), `queue` и `scheduler` ждут его готовности. Команды для README:

```bash
cp .env.example .env
docker run --rm -u "$(id -u):$(id -g)" -v "$(pwd):/var/www/html" -w /var/www/html \
  laravelsail/php85-composer:latest composer install --ignore-platform-reqs   # образ проверить; запасной — composer:2
./vendor/bin/sail up -d --build
# ключ, миграции и сборка фронта выполняются автоматически; альтернатива одной командой: ./bin/setup
```

## 6. Функциональные требования

### 6.1. Эндпоинт вебхуков — `POST /api/webhooks/marketplace` (P0)

| ID | Требование |
|---|---|
| FR-WH-01 | Принимает `POST`, тело — JSON UTF-8. Маршрут в `routes/api.php` (API-маршрутизация включается в `bootstrap/app.php` вручную, без `install:api`/Sanctum) |
| FR-WH-02 | Обязательные заголовки: `X-Webhook-Id`, `X-Webhook-Timestamp` (целое, Unix-секунды), `X-Webhook-Signature` в формате `sha256=<64 hex>`. Отсутствие/неверный формат → **401** |
| FR-WH-03 | Окно: `abs(now − timestamp) ≤ MARKETPLACE_WEBHOOK_TOLERANCE` (по умолчанию 300 с), в обе стороны. Иначе **401** |
| FR-WH-04 | Подпись: `hash_hmac('sha256', $timestamp . '.' . $request->getContent(), $secret)`, сравнение `hash_equals`; регистр hex нормализовать к нижнему. Несовпадение → **401**. Проверка выполняется **до** разбора JSON; тело в логи/ответ не попадает |
| FR-WH-05 | Невалидный JSON / не-UTF-8 → **400**. Несовпадение `X-Webhook-Id` и `body.id` → **400** |
| FR-WH-06 | Валидация базового конверта: `id` и `type` — непустые строки, `created_at` — корректная ISO 8601 дата-время со смещением, `data` — object; иначе **422**. Для известного типа обязательно `data.order`-object. Для неизвестного типа формат `data.order` не проверяется, чтобы расширение протокола не вызывало бесполезные повторы |
| FR-WH-07 | Неизвестный `type` при валидном базовом конверте → событие сохраняется (`outcome = ignored`), состояние и история заказа **не меняются**, письма **не** отправляются, ответ **200**. Если в известном типе `data.order.status` — строка, но значение не входит в известный enum статусов, событие также сохраняется как `ignored` с ответом **200**; заказ, история и письма не меняются. При повторе этих событий применяется общая дедупликация по `event.id`. Известные типы: `order.created`, `order.updated`, `order.paid`, `order.shipped`, `order.delivered`, `order.cancelled` |
| FR-WH-08 | Для известного типа и известного статуса валидируется полный снимок по `marketplace-webhooks.md`: `id`, `number`, `status`, `currency` (3 заглавные буквы, **не** ограничивать списком RUB/USD/EUR), `customer.{email,name,phone?}`, `items[].{sku,name,quantity≥1,price}`, суммы `^-?\d+\.\d{2}$`, `shipment` (null либо `{carrier,tracking_number,tracking_url}`), даты ISO 8601 с смещением. Отсутствующее поле, неверный тип или неверный формат → **422**; такой запрос не записывается в `webhook_events`. Неизвестное строковое значение `status` обрабатывается по FR-WH-07 до полной валидации остальных полей снимка |
| FR-WH-09 | Арифметика `total = Σ(price×qty) + delivery − discount` **не** является основанием для отказа; расхождение логируется как warning (A-17) |
| FR-WH-10 | Ответы: **200** с полем `status` — одним из значений `processed`, `duplicate`, `stale`, `ignored` или `rejected`; **401** подпись/время; **400** невалидный JSON или несовпадение ID; **413** тело больше 1 MiB; **422** невалидный базовый конверт или некорректный снимок известного статуса; **503** блокировка не получена либо Redis/БД недоступны (маркетплейс повторит доставку). Тела всех ответов — JSON, без payload и внутренних ошибок |
| FR-WH-11 | Для маршрута отключены throttle, CSRF и любые middleware, меняющие тело; все ответы `api/*` — JSON даже без `Accept` |
| FR-WH-12 | Ограничение тела — 1 MiB. В выбранном Sail используется `php artisan serve`, nginx нет: лимит проверяется на раннем этапе приложения по `Content-Length` и фактическому размеру сырых байтов; настройка PHP не должна молча обрезать тело. Превышение → **413**. Если позже добавляется reverse proxy, тот должен иметь такой же или больший лимит и возвращать совместимый ответ |
| FR-WH-13 (P2) | Ротация секрета: дополнительная переменная `MARKETPLACE_WEBHOOK_SECRET_PREVIOUS`, подпись принимается любым из двух секретов |

### 6.2. Идемпотентность, порядок и конкурентность (P0/P1)

| ID | Требование |
|---|---|
| FR-ORD-01 | **Идемпотентность по `event.id`.** Таблица `webhook_events` с уникальным индексом по `id`. Вставка события и применение снимка — в **одной транзакции**; повторная доставка (в т.ч. параллельная, неизвестного типа/статуса и «после успеха») → увеличивает `deliveries`, обновляет `last_received_at`, возвращает **200 `duplicate`**, не меняя исходные `payload`/`outcome` и заказ. Дополнительно хранить `payload_sha256`: если повтор с тем же `event.id` имеет другой хеш тела, считать его дублем, но писать warning `duplicate_payload_mismatch` без сохранения нового тела |
| FR-ORD-02 | **Версия заказа** = кортеж `(order.updated_at (UTC), event.created_at (UTC), event.id)`. Входящий снимок применяется, только если его версия **строго больше** версии, сохранённой в заказе. Иначе — **200 `stale`**: состояние заказа не меняется, письма не создаются (A-14, Q14) |
| FR-ORD-03 | Сравнение дат только как **моментов времени** (`CarbonImmutable::parse()->utc()`); в БД — `DATETIME` в UTC. Строковое сравнение ISO-дат запрещено |
| FR-ORD-04 | Применение снимка — **полная перезапись** полей заказа и позиций (`items` заменяются целиком, порядок позиций сохраняется) |
| FR-ORD-05 | Статус берётся из `order.status` снимка, а не из `type` события. Откат статуса (ручное исправление) допустим и применяется, если снимок свежее, **кроме выхода из терминальных статусов** (FR-ORD-09) (A-15, A-16) |
| FR-ORD-06 | Заказ создаётся из **любого** первого снимка (`order.paid` может прийти раньше `order.created`) |
| FR-ORD-07 | **Конкурентность:** на время обработки события берётся общая для вебхуков и отправки письма блокировка по заказу — `Cache::lock("order:{id}", config('marketplace.order_lock_lease'))` (Redis), ожидание — `config('marketplace.order_lock_timeout')` (по умолчанию не более 3 с); внутри транзакции также используется `SELECT … FOR UPDATE`. Не удалось взять блокировку вебхуком → **503**. Deadlock → повтор транзакции (`DB::transaction(…, attempts: 3)`), но суммарный бюджет запроса должен оставаться меньше 5 с: ретраи не должны нарушать дедлайн MarketHub; если безопасно завершить обработку в срок нельзя — вернуть **503** до истечения 5 с. SMTP timeout — 5 с, lease по умолчанию 15 с |
| FR-ORD-08 | Каждое событие с валидной подписью и валидным базовым конвертом фиксируется в `webhook_events` с исходом `applied`, `stale`, `ignored` или `rejected` (сырое тело сохраняется байт-в-байт). Невалидный JSON, несовпадение ID, неверный базовый конверт и некорректный снимок известного статуса возвращают соответствующий 4xx и не сохраняются. При дубле исходный `outcome` не заменяется на `duplicate`: `duplicate` — только HTTP-ответ повторной доставке |
| FR-ORD-09 | **Терминальные статусы — решение + допущение Q35**: по ответу пользователя на Q15 откаты из `delivered` и `cancelled` не допускаются. Дополнительно, в качестве консервативного допущения для реализации, запрещаются и переходы между самими терминальными статусами (`delivered → cancelled` и `cancelled → delivered`); PDF-экспорт не подтверждает, что это отдельное бизнес-правило. Поэтому любой более свежий снимок с другим статусом при текущем `delivered`/`cancelled` отклоняется: ответ **200 `rejected`**, `webhook_events.outcome = rejected`, `reject_reason = terminal_status`, warning в логе; состояние, история и письма не меняются. Снимок с тем же терминальным статусом (обновление данных/причины) применяется. Правило хранится в `config/marketplace.php` (`terminal_statuses`). В `DECISIONS.md` отдельно указать, что запрет перехода между двумя терминальными статусами — допущение, а не подтверждённое правило MarketHub. |

### 6.4. История статусов (P0, детали — P1)

`GET /api/orders/{id}` отдаёт `history` — «статусы, в которых побывал заказ, с моментом перехода **по данным маркетплейса**, в хронологическом порядке» (не время получения вебхука).

| ID | Правило (A-18, A-19) |
|---|---|
| FR-HIS-01 | Момент перехода `at`: `created` → `created_at`; `paid` → `paid_at`; `cancelled` → `cancelled_at`; `shipped`, `delivered` → `updated_at` снимка. Если «родное» поле `null` — `updated_at` |
| FR-HIS-02 | Из **каждого** принятого снимка (в т.ч. устаревшего) в историю добавляются «факты», которые из него следуют, если их ещё нет: `created @ created_at`; `paid @ paid_at` (если `paid_at ≠ null`); `cancelled @ cancelled_at` (если ≠ null); для снимков со статусом `shipped`/`delivered` — этот статус `@ updated_at`. Благодаря этому потеря/опоздание события не оставляет «дыр» (пример: пришёл `shipped`, `order.paid` потерян — `paid` восстановится по `paid_at`) |
| FR-HIS-03 | Если применённый снимок **откатывает** статус (ранг ниже текущего: `created=0, paid=1, shipped=2`, либо возврат `cancelled`/`delivered` в другой статус — **последнее запрещено**, FR-ORD-09), добавляется запись `(новый статус @ updated_at снимка)` — это момент ручного исправления |
| FR-HIS-04 | Вставка идемпотентна (`UNIQUE (order_id, status, at)`, `INSERT IGNORE`/`upsert`); вывод сортируется по `at ASC`, при равенстве — по рангу статуса, затем по `id` |
| FR-HIS-05 | Пример из OpenAPI (`created 13:02:11+03:00`, `paid 13:05:47+03:00`, `shipped 2026-10-22T06:40:03+00:00`) должен воспроизводиться на примерах `order-*.json` (в формате вывода UTC допустимо другое смещение при том же моменте) |

### 6.5. Письма покупателю (P0)

**Триггеры (A-22, A-28).** Письмо создаётся только по применённому снимку, который действительно меняет статус заказа на `paid`, `shipped` или `cancelled`. `duplicate`, `stale`, `ignored` и `rejected` писем не создают. При этом письмо-исправление при откате статуса не отправляется: например, свежая коррекция `shipped → paid` меняет состояние и историю, но не запускает повторное письмо «оплачен». Тип события не является источником статуса; требование обязательного совпадения `event.type` и `order.status` в ответах не было явно согласовано, поэтому оно не вводится. Обычные `order.created`, `order.updated` и `order.delivered` обычно не создают уведомления, если снимок не создаёт указанного перехода; если поведение маркетплейса в ручных коррекциях отличается, допущение фиксируется в `DECISIONS.md`. Если `order.paid` опоздало и снимок стал `stale`, письма нет.

| Тип | Тема (дословно) | Содержание |
|---|---|---|
| `paid` | `Заказ №{number} оплачен` | состав заказа (SKU, название, кол-во × цена = стоимость позиции), доставка, скидка, **итого** |
| `shipped` | `Заказ №{number} передан в доставку` | служба доставки, трек-номер, ссылка на отслеживание |
| `cancelled` | `Заказ №{number} отменён` | причина отмены; **если `paid_at ≠ null`** — «Деньги вернутся в течение 10 дней.» |

`{number}` — поле `number` (например, `MH-1048213`), символ «№» в теме — U+2116. Простой текст (`text/plain; charset=UTF-8`), без HTML. Получатель — `customer.email` из **текущего** состояния заказа. Данные письма берутся из **текущего состояния заказа на момент отправки**, а не из снимка события-триггера (если после `paid` пришёл свежий `order.updated`, состав в письме актуальный).

Суммы выводятся **дословно как в снимке** + код валюты: `4909.50 RUB` (A-26) — так проще сверять и нет локальных форматов.

Пример `paid`:

```text
Здравствуйте, Анна Смирнова!

Ваш заказ №MH-1048213 оплачен.

Состав заказа:
1. TSHIRT-BLK-M — Футболка базовая, чёрная, M: 3 × 1290.00 = 3870.00 RUB
2. CAP-NVY — Бейсболка "Classic" / синяя: 1 × 890.50 = 890.50 RUB

Доставка: 349.00 RUB
Скидка: 200.00 RUB
Итого: 4909.50 RUB
```

Правила надёжности писем:

| ID | Требование |
|---|---|
| FR-MAIL-01 | **Outbox:** запись `order_notifications` (`pending`) создаётся в **той же транзакции**, что и применение снимка; задание `SendOrderNotification` ставится в очередь после коммита (`afterCommit`) |
| FR-MAIL-02 | **Дедупликация** через `UNIQUE dedupe_key`: `paid` и `cancelled` — `{order_id}:{type}`; `shipped` — `{order_id}:shipped:{tracking_number}` (A-24, Q24). При создании outbox ключ использует tracking number события; перед отправкой `shipped`-письма ключ обязательно сверяется с номером отслеживания **текущего** снимка, поскольку тело письма строится по текущему состоянию. Если ключ нужно изменить — обновить его атомарно, а при уже существующей записи с целевым ключом пометить уведомление `skipped (duplicate_tracking)` и не отправлять письмо. Вставка `INSERT IGNORE`: дубль → письмо не создаётся |
| FR-MAIL-03 | **Проверка непосредственно перед отправкой**: задание получает тот же Redis-lock `order:{id}`, что и обработчик вебхука; внутри транзакции блокирует заказ через `FOR UPDATE` и проверяет матрицу допустимости. Если письмо недопустимо — `skipped` (`skip_reason = superseded`), `dedupe_key = NULL`. Распределённая блокировка удерживается до завершения SMTP-вызова и фиксации результата, поэтому вебхук не может сменить состояние между проверкой и отправкой. Lease блокировки должен превышать SMTP timeout; при занятом lock вебхук ждёт не более заданных 3 с и отвечает 503 для повтора |
| FR-MAIL-04 | **Захват перед отправкой:** под общей блокировкой выполнить `UPDATE … SET status='sending' WHERE id=? AND status='pending'`; 0 затронутых строк → выход. Два воркера не отправят одно письмо. Блокировка не заменяет атомарный захват строки БД; нужны оба механизма |
| FR-MAIL-05 | При однозначной временной ошибке отправки (SMTP недоступен) → `pending`, `attempts++`, повтор с backoff `10 с, 1 мин, 5 мин, 15 мин`, после 5 попыток → `failed`. Если воркер упал в состоянии `sending`, автоматически не переотправлять (приоритет «не дублировать»); запись помечается как зависшая для ручной диагностики. У SMTP нет общей с БД транзакции, поэтому строгое exactly-once недостижимо: политика — минимизировать дубли, принимая риск пропуска при падении в критическом окне |
| FR-MAIL-06 (P1) | Планировщик раз в минуту переставляет в очередь `pending`-уведомления старше 2 минут (Redis был недоступен при `dispatch`) |
| FR-MAIL-07 | Невалидный email получателя → `skipped (invalid_recipient)`, warning в лог |
| FR-MAIL-08 | `shipped` без `shipment` в текущем состоянии → `skipped (no_shipment)`, warning |

Допустимость письма в зависимости от **текущего** статуса заказа (A-23):

| Письмо ↓ / статус → | created | paid | shipped | delivered | cancelled |
|---|:-:|:-:|:-:|:-:|:-:|
| `paid` | ✗ | ✓ | ✓ | ✓ | ✗ |
| `shipped` | ✗ | ✗ | ✓ | ✓ | ✗ |
| `cancelled` | ✗ | ✗ | ✗ | ✗ | ✓ |

| FR-API-08 | Некорректные query-параметры (`status` вне enum, `per_page=0|101`, `page=0`, нечисловые) → **422** в стандартном JSON-формате Laravel (A-29) |

## 7. Алгоритм обработки события

```text
POST /api/webhooks/marketplace
 1. raw = $request->getContent(); лимит 1 MiB проверяется до разбора JSON
 2. обязательные заголовки, формат timestamp/signature валидны?       нет → 401
 3. |now − X-Webhook-Timestamp| ≤ tolerance?                          нет → 401
 4. проверить HMAC по timestamp + "." + raw через hash_equals         нет → 401
 5. json_decode(raw) успешен?                                         нет → 400
 6. X-Webhook-Id == body.id?                                          нет → 400
 7. проверить базовый конверт: непустые id/type, created_at с offset,
    data — object                                                    нет → 422
 8. если type неизвестен:
      в транзакции INSERT IGNORE webhook_events(outcome=ignored,
      order_id=NULL, payload, payload_sha256); при дубле deliveries++,
      last_received_at обновить; если хеш отличается — warning
      → 200 ignored или 200 duplicate; заказ и история не меняются
 9. для известного type проверить наличие data.order object,
    order.id — строка, order.status — строка                       нет → 422
10. если status неизвестен:
      сохранить событие как ignored с order_id и payload hash;
      при дубле — общая обработка duplicate; warning
      → 200 ignored/duplicate; заказ, история и письма не меняются
11. валидировать остальные обязательные поля снимка известного статуса
                                                                     нет → 422
12. Cache::lock("order:{order.id}", lease=15)->block(3)              не взят → 503
13. DB::transaction (retry при deadlock; lock освобождать в finally):
    a. INSERT IGNORE webhook_events(..., outcome=applied)
       вставка не состоялась → deliveries++, last_received_at обновить;
       несовпадение payload_sha256 → warning;
       заказ не менять; → 200 duplicate
    b. order = Order::lockForUpdate()->find(order.id)
    c. incoming = (order.updated_at, event.created_at, event.id) — UTC
       если order существует и incoming <= order.version:
            история += достоверные факты из снимка (FR-HIS-02);
            outcome=stale; commit → 200 stale
    d. если текущий status терминальный и новый status другой:
            outcome=rejected, reject_reason=terminal_status;
            warning; состояние/история/письма не меняются;
            commit → 200 rejected
    e. prev = order?->status; полностью перезаписать заказ и позиции;
       сохранить version и snapshot; записать факты истории и откат
    f. создать outbox-уведомление, если применённый снимок изменил статус
       на paid / shipped / cancelled и переход не является откатом, для
       которого Q28 запрещает письмо-исправление. Не требовать совпадения
       event.type со статусом: такой дополнительный фильтр не согласован.
    g. webhook_events.outcome=applied; commit
14. после коммита dispatch уведомления через afterCommit; если постановка
    не удалась, outbox sweeper обнаружит pending. → 200 processed

SendOrderNotification (Redis queue):
 1. загрузить notification; status != pending → выход
 2. получить тот же Cache::lock("order:{id}", lease=15)->block(3);
    если lock не получен — повторить задачу по политике очереди
 3. в DB-транзакции заблокировать Order через FOR UPDATE и проверить
    матрицу допустимости и валидность email/shipment; при запрете —
    skipped с причиной и освобождением dedupe_key
 4. атомарно захватить notification: status=pending → sending;
    если обновлено 0 строк — выход
 5. удерживая Redis-lock, отправить plain-text письмо с данными текущего
    заказа; SMTP timeout ≤ 5 с; записать sent/sent_at либо pending +
    attempts/backoff или failed; освободить lock в finally
```

## 13. Git и процесс сдачи

1. Репозиторий **публичный**, создан из шаблона; Laravel — в корне; `task/` не менять.
2. Коммиты небольшие и осмысленные; **описания на русском** (Q4), префиксы Conventional Commits (`feat`, `fix`, `test`, `docs`, `chore`, `refactor`). Предлагаемая последовательность: `chore: каркас Laravel 13 и окружение Sail` → `feat: схема данных заказов` → `feat: проверка подписи вебхуков` → `feat: идемпотентный приём событий` → `feat: применение снимка с учётом версии и терминальных статусов` → `feat: история статусов` → `feat: outbox и дедупликация писем` → `feat: письма покупателю и задание отправки` → `feat: API заказов` → `feat: админка на Inertia` → `docs: README и DECISIONS`. Тесты и обновление документации — в тех же коммитах, что и фичи (DOC-02).
3. Секреты и `.env` не коммитятся; `.env.example` коммитится.
4. Перед сдачей: чистый `git clone` → команды из README → прогон `send-event.php` по всем примерам → письма видны в Mailpit → `composer check` зелёный → проверка DOC-04.
5. Если часть не сделана — лучше меньше, но до конца; невыполненное и план — в `DECISIONS.md`.

### 16.2. Принятый вариант Q3 и технические допущения

**Q3 закрыт: выбран вариант A.** Страницы Inertia получают данные через props от серверных контроллеров. Для списка заказов используется общий `OrderListQuery`, одинаковые правила фильтрации/сортировки и общие Resources/мапперы с API. Браузер админки не делает запрос к `/api/orders`; API остаётся самостоятельным публичным интерфейсом и проверяется контрактными тестами по `task/openapi.yaml`. Варианты A и B и их плюсы/минусы приведены в §6.7 для объяснения выбора. В `DECISIONS.md` записать, что вариант A выбран ради идиоматичного Inertia UX, меньшего количества клиентского кода и повторного использования серверной бизнес-логики.

**Q35 зафиксирован как консервативное допущение для реализации, а не как подтверждённое правило MarketHub.** Из ответа Q15 следует, что откаты из `delivered` и `cancelled` запрещены; отдельного ответа о переходе `delivered → cancelled` в экспорте нет. Чтобы избежать неоднозначного финального состояния, в рамках тестового задания запрещать любой переход из `delivered`/`cancelled` в другой статус, включая переход между этими двумя статусами. Обновление данных при сохранении того же терминального статуса разрешено. В `DECISIONS.md` обязательно указать происхождение и причину допущения.

| Q | Тема | Рабочее решение | Статус |
|---|---|---|---|
| 35 | Переходы между терминальными статусами | Любой переход из `delivered`/`cancelled` в другой статус запрещён; снимок с тем же статусом применяется | Допущение принято для реализации; не подтверждено документацией MarketHub |
| 36 | TypeScript или JavaScript | TypeScript (`<script setup lang="ts">`, `vue-tsc --noEmit`) | Не отвечено в экспорте; рабочее техническое значение по умолчанию |

Q3 больше не является открытым вопросом. Из Q36 и Q38 остаются неподтверждёнными технические детали, которые не блокируют реализацию; при необходимости их можно уточнить позднее, но выбранные значения нужно отразить в `DECISIONS.md`.

### 16.3. Вопросы для `DECISIONS.md`

В `DECISIONS.md` зафиксировать **допущения, которые нельзя уточнить у MarketHub в рамках тестового задания**: Q13 — поведение для новых типов и статусов; Q14 — монотонность `updated_at` и tie-break при точности до секунды; Q16 — отсутствие в схеме адреса, `shipped_at` и `delivered_at`; Q35 — консервативный запрет перехода между двумя терминальными статусами, который расширяет подтверждённый ответ пользователя на Q15 и потому не должен представляться как правило, подтверждённое MarketHub. По бизнес-правилам — Q22–Q28: письма при опоздавших событиях, повторные письма с новым треком, тексты/суммы и компромисс при сбоях отправки. Отдельно указать, что Q3 решён в пользу варианта A.

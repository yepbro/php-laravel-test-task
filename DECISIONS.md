# Принятые решения

Краткая версия (§12.1 ТЗ). Полный журнал с обоснованиями — разделы
«Задача 003…044, 047» и сводные разделы T-045 —
в [`docs/DECISIONS-log.md`](docs/DECISIONS-log.md); детали — в коде
и `docs/`.

## Ключевые решения

- **Окружение** — стандартный Sail (PHP 8.5, MySQL 8.4, Redis `7-alpine`,
  Mailpit); очередь — Horizon и отдельный сервис `scheduler`; ключ,
  миграции и сборка фронта — идемпотентный стартовый процесс контейнера
  `laravel.test`, чистый запуск одной командой `./bin/setup`. Порты:
  приложение `80`, MySQL `3306`, Redis `FORWARD_REDIS_PORT`, Mailpit
  UI `8025`.
- **Вебхук** — подпись HMAC проверяется по сырым байтам тела в middleware
  до JSON-разбора (`hash_equals`, fail-closed при пустом секрете); лимит
  тела 1 MiB — в приложении (nginx в Sail нет).
- **Идемпотентность и порядок** — уникальность `webhook_events.id`
  (повтор → `200 duplicate`, `deliveries` растёт); версия снимка — кортеж
  `(order.updated_at, event.created_at, event.id)` по моментам UTC,
  применяется только строго большая; Redis-lock заказа + `SELECT … FOR
  UPDATE`, занятая блокировка → 503; вся запись — одна транзакция.
- **Письма** — transactional outbox (`order_notifications`) с dedupe-ключами
  `{order}:paid`, `{order}:cancelled`, `{order}:shipped:{track}`; повторная
  проверка допустимости в job под блокировкой, retry/backoff, sweeper
  потерянных `pending`; при сбоях приоритет «не дублировать».
- **API и качество** — только контракт `task/openapi.yaml` + `GET /up`,
  ответы валидируются контрактными тестами (`opis/json-schema`); деньги —
  decimal-строки без float, даты — UTC `+00:00`; Pint + Larastan level 10
  без baseline, PHPUnit (624 теста) на MySQL 8.4, CI из трёх джоб, автотест
  синхронности `.env.example`, браузерные smoke-тесты Playwright (11).

## Допущения маркетплейса и бизнес-правил

Вопросы, которые нельзя уточнить у MarketHub в рамках задания (§16.3 ТЗ).

- **Q3 — стек и источник данных админки (решение владельца, с пересмотром).**
  Изначально (26.10.2026) выбран вариант A: данные через Inertia props
  и общий серверный `OrderListQuery`; 27.10 пересмотрено в пользу
  **гибрида**: Inertia остаётся оболочкой (маршруты, layout, вспомогательные
  props — например, русские подписи статусов), а данные заказов браузер
  запрашивает у методов контракта `GET /api/orders` и
  `GET /api/orders/{id}`. Причины: dogfooding контракта и возможность
  вынести фронтенд в отдельный SPA без изменений бэкенда. Следствия:
  состояния загрузки/ошибок на клиенте, 404 карточки — клиентское
  состояние, обязательные Playwright smoke-тесты.
- **Q35 — терминальные статусы (консервативное допущение, правилом MarketHub
  не подтверждено).** Ответ Q15 запрещает откаты из `delivered`/`cancelled`;
  переход `delivered ↔ cancelled` документацией не описан. Чтобы избежать
  неоднозначного финального состояния, запрещён **любой** переход из
  терминального статуса (включая `delivered ↔ cancelled`); снимок с тем же
  терминальным статусом применяется как обновление данных. Отклонённое
  событие сохраняется с `outcome=rejected` (HTTP 200). При разъяснении
  MarketHub достаточно поменять правило в конфиге и тестах.
- **Q13** — неизвестный `type` → 200 `ignored` без требования `data.order`;
  неизвестный строковый `status` → `ignored` без изменения заказа.
- **Q14** — монотонность `updated_at` не гарантируется, точность — секунда;
  ничья разрешается детерминированно кортежем версии.
- **Q16** — «адрес» из описания `order.updated` игнорируется; полей
  `shipped_at`/`delivered_at` в схеме нет — момент перехода берётся из
  `updated_at` снимка.
- **Q22–Q28 (письма)** — триггер: только применённый снимок, реально меняющий
  статус на `paid`/`shipped`/`cancelled` (stale/duplicate/rejected/ignored
  писем не создают); допустимость на момент отправки — матрица §6.5;
  повторное `shipped` с тем же треком не отправляется, с новым —
  отправляется; при откате статуса письмо-исправление не отправляется
  (Q28); суммы и тексты — дословно из текущего состояния + код валюты;
  при сбоях отправки — «не дублировать» (Q25).
- **Q36/Q38** — TypeScript во фронте и английские идентификаторы кода/БД/JSON
  — рабочие технические значения по умолчанию; человекочитаемые тексты
  (UI, письма, коммиты, документация) — русские.

## Ограничения и остаток

Что не реализовано буквально и как бы делали (подробности — в журнале):

- **S-04/S-28 как P1-интеграционные** (параллельные доставки, письмо через
  Mailpit API) — вне PHPUnit-сьюта: требуют поднятого стенда. Способ:
  процессные тесты (`Symfony\Process`) против тест-сервера.
- **Ротация секрета** `MARKETPLACE_WEBHOOK_SECRET_PREVIOUS` (FR-WH-13, P2) —
  не реализована. Способ: проверка второго секрета в middleware.
- **Блок «Письма» в карточке админки** (FR-ADM-03, P2) — уведомлений нет
  в контракте `GET /api/orders/{id}`, а эндпоинты вне контракта запрещены
  (FR-API-11). Способ: расширение контракта.
- **JSON-логи в stderr** (NFR-06) — канал `stack`/`single`; машинные токены и
  контекст `event_id`/`order_id` в сообщениях есть. Способ: канал `stderr`
  с JSON-formatter.
- **Локализация валидации API** (NFR-12) — тексты 422 английские. Способ:
  `lang/ru` + `APP_LOCALE=ru` (без каталога локаль сломала бы тексты).
- **Playwright-набор в CI** — e2e гоняется локально (`sail composer e2e`).
  Способ: джоба CI с полным стеком (MySQL, сид, сборка, браузеры).

## Использование ИИ

Проект выполнен владельцем в паре с ИИ-агентами: ТЗ и декомпозиция —
с ИИ-ассистентом (значимые решения — порты, пересмотр Q3, структура
документации — принимал владелец); каждая задача реализовывалась отдельным
субагентом («проектирование → реализация → тесты → документация») и
ревьюилась независимым ИИ-агентом (read-only, P0–P3, до 3 раундов);
верификация и влития — основной сессией под контролем владельца.

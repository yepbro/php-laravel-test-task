# Принятые решения

Журнал технических решений и отклонений от исходного текста ТЗ.
Каждая запись привязана к задаче, в которой решение принято; файл пополняется

## Окружение (Sail)

- **Порты окружения приведены к фактической конфигурации** (T-002, решение
  пользователя). Приложение публикуется на `80` (`APP_PORT`), MySQL — на
  `3306` (`FORWARD_DB_PORT`), Redis — через `FORWARD_REDIS_PORT` (по
  умолчанию `6379`; в локальном `.env` может быть переопределён, например на
  `6380` — это нормальная ситуация). Исходные значения ТЗ v1.4 (8080/3307/без
  публикации порта Redis) заменены; ТЗ и план обновлены синхронно
  (docs-коммит `50d4ced`), рассинхронизации с `compose.yaml` по портам нет.
- **Redis закреплён на образе `redis:7-alpine`** (T-002). Плавающий тег
  `redis:alpine` фактически разворачивал Redis 8.x и не гарантирует
  мажорскую версию 7, требуемую ТЗ §5.2; закреплённый тег делает окружение
  воспроизводимым. Данные в volume `sail-redis` сохраняются при смене образа;
  исключение — переход вниз с 8.x: устаревший `dump.rdb` от Redis 8 (формат
  RDB 15) нечитаем для Redis 7, на дев-этапе дамп был удалён (только
  эфемерные данные, бизнес-данных в Redis на момент задачи нет).

## Архитектура админки — пересмотр Q3

**(решение пользователя, 27.10.2026, вне цикла задач; ТЗ поднято до v1.5)**

Изначально Q3 был закрыт вариантом A (Inertia props + общий серверный
`OrderListQuery`/Resources). Пересмотрено в пользу **гибрида**:

- админка остаётся на Inertia — маршруты `/admin/orders*`, layout,
  навигация, русская локаль;
- данные заказов браузер запрашивает у методов контракта
  `task/openapi.yaml`: `GET /api/orders` (список) и
  `GET /api/orders/{id}` (карточка); заказы через props не передаются;
- props несут только вспомогательные данные, которых нет в контракте
  (например, опции фильтра статусов с русскими подписями).

Причины: dogfooding контракта (админка — реальный клиент OpenAPI) и
возможность в будущем вынести фронтенд в отдельный SPA без изменений
бэкенда. Принятые следствия: состояния загрузки/ошибок на клиенте,
пагинация по `meta` (ссылки `links` из API ведут на `/api/orders` и для
навигации админки не используются), 404 карточки — клиентское состояние
по 404 от API, **обязательные** браузерные smoke-тесты Playwright
(FR-ADM-07, задача 047). Серверный `OrderListQuery` и Resources остаются
реализацией самого API (задачи 036–037); API как и раньше проверяется
независимыми контрактными тестами (FR-API-10).

Отражено: ТЗ v1.5 §6.7 (FR-ADM-04/05/07), §8 (S-32/S-33), §11, §12.2,
§16.1–§16.3, §17; `plan/tasks.md` — задачи 011, 013, 036, 039–041,
045–047 (новая 047 — Playwright).

## Задача 003. Миграции доменных таблиц

### Внешние ключи при удалении заказа

ТЗ §6.3 явно задаёт FK только для `order_items` (cascade) и
`order_notifications` (`order_id FK`); поведение при удалении заказа оставлено
на решение исполнителя.

| Таблица | Правило | Обоснование |
|---|---|---|
| `order_items.order_id` | FK → `orders.id`, `ON DELETE CASCADE` | Прямо указано в §6.3 |
| `order_status_history.order_id` | FK → `orders.id`, `ON DELETE CASCADE` | История — производные данные заказа; задача 008 ожидает cascade наравне с позициями |
| `order_notifications.order_id` | FK → `orders.id`, `ON DELETE CASCADE` | Outbox-запись создаётся в одной транзакции с заказом (FR-MAIL-01), заказ всегда существует; уведомления — часть жизненного цикла заказа. Приложение заказы не удаляет, правило актуально только для ручных операций |
| `webhook_events.order_id` | **Без FK**, обычный индекс | По алгоритму §7 (шаг 13a) событие вставляется в `webhook_events` **до** создания/обновления заказа: для первого снимка заказа строки в `orders` ещё нет, FK нарушался бы. Кроме того, события неизвестных типов хранятся с `order_id = NULL`. Журнал событий — независимый аудит, связь остаётся мягкой ссылкой; при удалении заказа строки событий сохраняются |

### Длины и типы полей, не заданные ТЗ явно

- `webhook_events.type` — `VARCHAR(32)`: известные типы ≤ 15 символов, запас
  на расширение списка типов без смены схемы.
- `orders.status`, `order_status_history.status`,
  `webhook_events.outcome`, `order_notifications.type/status` —
  `VARCHAR(16)`: максимальное значение (`cancelled`/`rejected`) = 9 символов.
- `webhook_events.reject_reason`, `order_notifications.skip_reason` —
  `VARCHAR(32)`: `terminal_status`/`duplicate_tracking`/`invalid_recipient`.
- `orders.shipment_carrier`, `orders.shipment_tracking_number`,
  `order_items.sku` — `VARCHAR(64)`. Длина трек-номера согласована с
  `dedupe_key VARCHAR(191)`: `{order_id ≤ 64}:shipped:{tracking_number ≤ 64}`
  даёт максимум 137 < 191 байт — ключ всегда помещается.
- `orders.shipment_tracking_url` — `VARCHAR(512)`: URL заметно длиннее
  артикулов и трек-номеров.
- `webhook_events.signature_timestamp` — знаковый `INT` (Unix-секунды), как в
  ТЗ; `deliveries INT NOT NULL DEFAULT 1` и `order_notifications.attempts INT
  UNSIGNED NOT NULL DEFAULT 0` — счётчики.
- `order_items.position` — знаковый `SMALLINT`, `quantity` — `INT UNSIGNED`:
  буквальное следование §6.3.
- `cancel_reason`, `last_error` — `TEXT NULL` (свободный текст
  причины/ошибки).

### Системные временные метки

- `created_at`/`updated_at` (Eloquent `timestamps()`) — только в `orders`
  (§6.3: «техн.») и `order_notifications` (§6.3: «timestamps»). В
  `order_items`, `order_status_history` и `webhook_events` системных меток
  нет — ТЗ их не указывает; у событий журнала собственное время
  `received_at`/`last_received_at`/`processed_at` (DATETIME, UTC).
- Все доменные даты — `DATETIME` (точность 0), хранение в UTC; суммы — только
  `DECIMAL(12,2)`, плавающих типов в схеме нет (проверяется тестом).

### Индексы

Индексы по §6.3: `orders(number)`, `orders(status, placed_at)`,
`orders(customer_email_normalized, placed_at)`, `orders(placed_at, id)`,
уники `order_items(order_id, position)`,
`order_status_history(order_id, status, at)` + индекс `(order_id, at, id)`,
`order_notifications(dedupe_key)`. Сверх ТЗ добавлен один индекс
`webhook_events(order_id)` (решение исполнителя) — для выборки событий
конкретного заказа в отладке и админке; §6.3 для `webhook_events` задаёт
только PK. Служебные индексы под будущие задачи (sweeper зависших
`pending`, retention-очистка `webhook_events`) не добавляются превентивно —
их добавит соответствующая задача, если профиль нагрузки этого потребует.

### Очереди

`jobs`/`job_batches`/`failed_jobs` берутся из стандартной миграции
`0001_01_01_000002_create_jobs_table.php` — не дублируются (проверяется
тестом).

## Задача 004. PHP Enums домена

### Состав enum'ов и соответствие БД/API

`App\Enums\{OrderStatus, NotificationType, NotificationStatus, EventOutcome}`
— string-backed, строковые значения дословно из ТЗ и совпадают со значениями
в колонках VARCHAR(16) из задачи T-003 и в API: `created|paid|shipped|
delivered|cancelled`, `paid|shipped|cancelled`, `pending|sending|sent|
skipped|failed`, `applied|stale|ignored|rejected`. Состав и значения
зафиксированы unit-тестами (включая проверку `from()` → `ValueError` /
`tryFrom()` → null на несуществующих значениях — приведение типа ничего
не маскирует).

### Ранги OrderStatus для сортировки истории

ТЗ (FR-HIS-03/FR-HIS-04) фиксирует ранги только не-терминальных статусов:
`created=0, paid=1, shipped=2`. Ранги `delivered=3` и `cancelled=4` —
решение исполнителя по смыслу сортировки истории: прогресс
`shipped → delivered` не должен считаться откатом, а при равном моменте
`at` порядок записей должен быть детерминированным (`created, paid,
shipped, delivered, cancelled`). Ранг используется только в механике
истории статусов — сортировка при равном `at` (FR-HIS-04) и обнаружение
отката для записи факта в историю (FR-HIS-03) — и не является
универсальным правилом допустимости переходов; переходы реализуются
сервисами по FR-ORD-05/FR-ORD-09.

### Терминальные статусы

Набор терминальных статусов Q35 (`delivered`, `cancelled`) пока
захардкожен в `OrderStatus::isTerminal()` с PHPDoc-ссылкой на Q35;
`config('marketplace.terminal_statuses')` появится в задаче T-009,
после чего сервисы переходов будут читать его. Чтобы не плодить два
источника истины, в T-009 связать их: либо `isTerminal()` переводится
на чтение конфига, либо конфиг заполняется case'ами enum'а с
тестом-сверкой (выбор — за задачей T-009).

### `duplicate` не входит в EventOutcome

По FR-ORD-01/FR-ORD-08 `duplicate` — только HTTP-ответ повторной
доставке; исходный `outcome` события в журнале при дубле не заменяется.
Поэтому `duplicate` — не case `EventOutcome` (зафиксировано тестом).
Словарь HTTP-ответа (FR-WH-10: `processed|duplicate|stale|ignored|rejected`)
шире журнала: `applied` отдаётся наружу как `processed`; маппинг —
задача T-010 (отмечено в PHPDoc enum).

## Задача 005. Eloquent-модели и связи

### Имя модели истории и имя связи

- Модель истории называется **`OrderStatusHistory`** (не `OrderStatusEntry`):
  совпадает с таблицей `order_status_history` из T-003 и читается как
  «запись истории статусов заказа». `$table` задан явно — автопредсказание
  Laravel по имени класса дало бы `order_status_histries`.
- Связь на `Order` названа **`history()`** по §6.6 ТЗ (eager loading
  `items`/`history`); API-поле `history[]` (FR-API-05) маппится из неё
  без переименований.

### Ключи и fillable

- `Order` и `WebhookEvent`: `$incrementing = false` +
  `protected $keyType = 'string'` — ключ назначает MarketHub (id заказа
  / `event.id`), а не БД (§6.3). Оба свойства переопределяются без типов
  — родительские объявления в Laravel нетипизированы.
- `id` включён в `$fillable` этих двух моделей: ключ приходит из снимка
  вебхука и задаётся при создании записи. У `OrderItem`,
  `OrderStatusHistory`, `OrderNotification` PK автоинкрементный и в
  `$fillable` не входит.

### Касты

- Суммы — `decimal:2`: в Laravel 13 это `Brick\Math\BigDecimal::toScale(2,
  HalfUp)`, то есть **строка** с двумя знаками, float не возникает
  (§6.3 «Decimal как строковое представление»). PHPDoc-тип — `string`.
- Даты MarketHub и метки журнала — `datetime`. Приложение глобально
  использует immutable-даты (`Date::use(CarbonImmutable::class)` в
  `AppServiceProvider` стартового комплекта), что соответствует
  FR-ORD-03, поэтому фактический тип каста и PHPDoc — `CarbonImmutable`
  (nullable-колонки — `CarbonImmutable|null`).
- `WebhookEvent::$payload` намеренно **без** каста: сырые байты тела
  (FR-ORD-08) хранятся и читаются байт в байт; JSON-разбор — задача
  обработчика (T-021), не модели.
- Счётчики и числа (`quantity`, `position`, `signature_timestamp`,
  `deliveries`, `attempts`) приведены явным `'integer'`-кастом.
- `Order::$snapshot` — `'array'`. Особенность MySQL: JSON-колонка
  нормализует порядок ключей объекта, round-trip порядок не сохраняет
  (зафиксировано тестом — сравнение по ключам, а не всего массива).

### Системные даты и даты MarketHub

- Системные `created_at`/`updated_at` есть только у `Order` и
  `OrderNotification` (ровно как в миграциях T-003); у `OrderItem`,
  `OrderStatusHistory`, `WebhookEvent` — `public $timestamps = false`,
  у событий журнала собственные метки `received_at`/`last_received_at`/
  `processed_at`.
- Группы не смешиваются ни в кастах, ни в PHPDoc, ни в логике: API
  использует даты MarketHub (`placed_at`, `source_updated_at` —
  FR-API-07), системные метки наружу не выходят. Независимость
  зафиксирована тестом: `touch()` меняет `updated_at`, не трогая
  `placed_at`/`source_updated_at`.

### Связи и их типизация

- `Order::items()/history()/notifications()` — hasMany; обратные связи —
  `order(): BelongsTo`.
- `WebhookEvent::order()` — belongsTo по мягкой ссылке `order_id` без FK
  (решение T-003: событие вставляется до создания заказа), поэтому
  `@property-read Order|null $order` — связь может быть null.
- PHPDoc-типизация под Larastan level 10 без подавлений: `@property` для
  всех колонок с типами, совпадающими с фактическим возвратом кастов;
  связи — `@return HasMany<X, $this>` / `BelongsTo<X, $this>` плюс
  `@property-read Collection<int, X>`.
- Бизнес-логика, скопы и хелперы в модели не добавлялись (не требуются
  текущему коду); `HasFactory` не подключён — фабричные классы и трейт
  добавит задача T-006.

### Из код-ревью: что осталось

- P2-1 из ревью T-005 (`tests/` вне путей `phpstan.neon`) — **окончательно
  отклонён по решению владельца проекта**: `tests/` сознательно не
  покрывается PHPStan, чтобы не раздувать тестовый код типизацией
  (отступление от перечня путей §5.1 ТЗ). Правило закреплено в
  `AGENTS.md` (раздел «Проверки»); при последующих ревью отсутствие
  `tests/` в `paths` недочётом не считается.

## Задача 006. Фабрики доменных моделей

### Согласованность по умолчанию и states

- Definition каждой фабрики даёт непротиворечивую запись без переопределений:
  `OrderFactory` — заказ в статусе `created` (nullable-поля NULL,
  shipment-тройка NULL вместе, версия снимка = `placed_at + 1 с`),
  `WebhookEventFactory` — известный тип с исходом `applied`,
  `OrderNotificationFactory` — `pending`-запись outbox.
- Статусные states `created/paid/shipped/delivered/cancelled` применяют
  **цельные наборы**: свой статус, свои даты MarketHub, обнуление чужих
  полей и пересчёт версии снимка (`source_updated_at` состояния,
  `version_event_created_at = source_updated_at + 1 с`, новый
  `version_event_id` — как в конверте события из task/examples).
- `cancelled()` не трогает `paid_at`: по умолчанию это отмена
  неоплаченного заказа (S-09), цепочка `paid()->cancelled()` — отмена
  оплаченного (S-08). `shipped()`/`delivered()` заполняют `paid_at`,
  если его нет (снимок shipped восстанавливает факт оплаты, S-07).
  `delivered()` сохраняет существующую shipment-тройку после
  `shipped()`, иначе генерирует согласованную (URL содержит трек-номер).
- `paid`-снимок: `source_updated_at` = `paid_at` (указывает ровно на
  `greaterThanOrEqual`, не строгое `>`) — отражает реальные примеры
  (`updated_at` снимка совпадает с моментом оплаты).

### Snapshot: форма и согласование

- Snapshot строится в форме снимка MarketHub (`task/examples/*.json`):
  `id/number/status/currency/customer{email,name,phone}/items/
  delivery_price/discount/total/shipment{carrier,tracking_number,
  tracking_url}/paid_at/cancelled_at/cancel_reason/created_at/updated_at`.
- Согласование — замыканием в `definition` (видит финальные атрибуты
  после states и переопределений): snapshot зеркалит строку **на момент
  создания записи**; `items` — `[]`, пока не вызван `withItems()`.
- Формат внутри snapshot: суммы — строки с двумя знаками, даты — ISO 8601
  UTC (`+00:00`). Парсер снимков — T-021; формат словаря снимка в фабрике
  выбран по входным примерам и не является контрактом до T-021.

### Деньги

- Генерация сумм без float: целые копейки → `BigDecimal::of(n)
  ->dividedBy(100, 2)` → строка с двумя знаками (для OrderFactory и
  OrderItemFactory). Числовые переопределения безопасны: каст `decimal:2`
  (BigDecimal, HalfUp) гарантирует строку с двумя знаками (покрыто
  тестом: `total => 100` → `'100.00'`, `'5.5'` → `'5.50'`).
- Арифметика `total = Σ(subtotal) + delivery − discount` фабрикой НЕ
  навязывается: ТЗ допускает расхождение (S-27, warning-only), а
  фикстурам с расхождением нужно уметь существовать по умолчанию.

### Позиции и история

- `OrderItemFactory`: `position` = `max(position) + 1` по заказу — при
  создании позиций по одной инкрементируется автоматически (в т.ч. для
  вложенной фабрики заказа). Для пакета `count()` одного заказа позиции
  передаются явно (Laravel разрешает атрибуты всего батча до вставки);
  `OrderFactory::withItems(N)` делает это сам и синхронизирует
  `snapshot['items']` с созданными строками.
- `OrderFactory::withHistory()` строит факты по FR-HIS-02 из полей
  записи (created@placed_at, paid@paid_at, cancelled@cancelled_at,
  shipped/delivered@source_updated_at); `OrderStatusHistoryFactory::
  forOrder()` — факт текущего статуса заказа с `at` из «родного» поля
  по FR-HIS-01. Оба не нарушают UNIQUE(order_id, status, at).

### События вебхуков

- `payload` — минимальный валидный конверт (`id/type/created_at/
  data.order.id`), согласованный с атрибутами записи; «настоящие»
  подписанные тела для HTTP-тестов остаются за `task/examples` (T-015).
- `payload_sha256` = `hash('sha256', payload)` считается от **финального**
  payload (ключ `payload` в definition стоит раньше и резолвится первым —
  включая явное переопределение payload) и переопределяется явно.
- `processed_at = received_at` по умолчанию: все исходы `EventOutcome` —
  конечные состояния обработки. `unknown()` (S-18) и `ignored()` (S-36)
  разделены: первый меняет тип события, второй — только исход.

### Уведомления

- Definition создаёт заказ, согласованный с типом письма по матрице §6.5
  (paid → оплаченный, shipped → отправленный, cancelled → отменённый),
  id заказа предгенерируется, чтобы вложенный заказ получил известный
  фабрике id; `dedupe_key` (FR-MAIL-02) строится замыканием от финальных
  `order_id`/`type` — включая явные переопределения (для `shipped`
  трек-номер берётся из итогового заказа; у заказа без shipment хвост
  ключа пуст — нестандартная комбинация под skip-ветку FR-MAIL-08).
- `recipient`/`subject` по умолчанию NULL: тело письма строится по
  текущему состоянию заказа в момент отправки (§6.5), а не при создании
  outbox-записи. State `sent()` заполняет их из заказа (тема — дословно
  по §6.5, включая «№» U+2116); `skipped()` освобождает `dedupe_key`
  (FR-MAIL-03), `failed()` — attempts 5 с last_error (FR-MAIL-05).
- `forOrder(Order)` пересчитывает `dedupe_key` по FR-MAIL-02 от этого
  заказа с учётом финального `type` записи (в т.ч. переопределённого
  при `create()`).

### Прочее

- Замыкания, передаваемые в `state()`, не объявляются `static`: Laravel
  делает `$state->bindTo($factory)` (на PHP 8.5 это deprecation-ошибка).
  Замыкания `definition`/`afterCreating` не биндятся и могут быть
  `static` (в основном так и есть; единичные не-static — эквивалентны).
- `@use HasFactory<…>` размещён на самом `use`-выражении внутри класса
  (как в `User`) — так PHPStan level 10 разрешает генерик трейта;
  `newFactory()` не нужен, имена фабрик следуют конвенции.
- `withItems(N)` при `N < 1` — no-op; `delivered()` после `shipped()`
  не откатывает хронологию версии снимка (правки по итогам ревью T-006).
- Фабрики не обращаются к MarketHub, почте и Redis: только Faker,
  `Str`, `BigDecimal` и БД (позиции/история/dedupe-ключ).

## Задача 007. Сидеры демо-данных

### Повторный запуск: полная пересборка, а не идемпотентность

`db:seed` предсказуем через **полную пересборку** demo-набора: перед созданием
очищаются только пять доменных таблиц (дети раньше родителей — порядок уважает
FK из T-003), остальные таблицы не затрагиваются (зафиксировано тестом на
`users`). Идемпотентный `updateOrCreate` отвергнут: потребовал бы фиксированных
id или сопоставления по бизнес-ключам и ветки «обновлять или пропускать»,
предсказуемость — хуже, а цель демо-набора — именно «ровно заявленный состав».
Очистка — `DELETE`, не `TRUNCATE`: TRUNCATE в MySQL требует
`FOREIGN_KEY_CHECKS=0` и является DDL с implicit commit, который сломал бы
транзакции RefreshDatabase в тестах; на демо-объёмах разницы в скорости нет.

### Production-защита в два уровня

- `DatabaseSeeder` в production **не вызывает** демо-сидер (warn и выход) —
  автоматический запуск исключён (требование чек-листа T-007).
- Сам `DemoOrdersSeeder` при обнаружении production бросает `RuntimeException` —
  закрывает явный вызов `db:seed --class=DemoOrdersSeeder --force` и программный,
  которые проходят мимо confirmToProceed самой команды.

Проверка окружения — `app()->environment('production')` (container-binding `env`,
не `config('app.env')`): в тестах переопределяется `$this->app->instance('env',
'production')`.

### Конфиг-точка объёма: `config/seeding.php`

Ключ `seeding.demo_orders` ← `env('SEED_DEMO_ORDERS', 30)`; правило «`config()`
вместо `env()` вне конфигов» соблюдено, переменная добавлена в `.env.example`
тем же коммитом (FR-ENV-04). Отдельный минимальный конфиг-файл, а не секция в
`config/app.php`: сидирование — самостоятельная забота dev-окружения;
`config/marketplace.php` не создаётся — это задача T-009. Дефолт 30 — три полных
цикла паттерна генератора (~6 заказов на статус, вторая страница пагинации при

`InvalidArgumentException` — молча выдать набор без какого-то статуса хуже,
чем явная ошибка конфигурации.

### Воспроизводимость: seed Faker + индексные паттерны

`fake()->seed(20261027)` и детерминированные циклы по индексу (статусы — 10,
позиции — 5, email-пул — 5, без телефона — каждый 6-й) дают структурно
воспроизводимый набор: при одинаковом объёме повторный запуск создаёт те же
номера, email, распределение статусов/позиций и интервалы `placed_at` (тест
сравнивает отпечаток набора дважды). Случайными остаются генерируемые фабриками
идентификаторы (`Str::random`/ULID) и «плавающий» якорь времени `now()` — оба
не влияют на проверку фильтров/сортировки/пагинации; тесты фиксируют время
через `travelTo`. `placed_at = now() − 137·i` минут: уникальные значения для
упорядочения `placed_at DESC` и размазанные даты (30 заказов ≈ 2,9 дня,
200 ≈ 19 дней).

### Демо-значения фильтруемых полей

Пул из пяти email с разным регистром исходного написания (`Anna@Shop.Test`,
`boris@shop.test`, …) назначается каждому третьему заказу: нормализованные
значения совпадают и повторяются — фильтр `email` (FR-API-02, точное совпадение
без учёта регистра) имеет и одиночные, и повторные адреса. События вебхуков —
id события совпадает с `version_event_id` заказа, тип согласован со статусом
(каждый 5-й), плюс два «журнальных»: неизвестный тип с `order_id` NULL (S-18)
и повторная доставка (S-02), привязанная к самому свежему заказу набора.
Уведомления — только заказам paid/shipped/cancelled (матрица §6.5), тип
задаётся явно по статусу (не случайный), сценарии покрывают все пять статусов
outbox. Базовые атрибуты (`placed_at`, email) цепляются `state()` **до**
статусных states фабрики: `paid()`/`shipped()`/… вычисляют свои даты от
`placed_at`, а `create()`-атрибуты мержатся последними.

## Задача 009. Конфигурация и скелет доменного слоя

### Структура слоя — по §10 ТЗ, без `app/Domain/`

Доменный слой размещён по структуре §10 ТЗ: DTO — `app/Data/`
(`MarketplaceEvent`, `OrderSnapshot` + вложенные `OrderCustomer`/
`OrderItemSnapshot`/`OrderShipment`, `Version`, `HistoryFact`),
доменные правила — `app/Support/` (`Money`, `SnapshotVersionComparator`,
`HistoryBuilder`, `NotificationPolicy`), исключения — `app/Exceptions/
Webhook/`. Отдельный каталог `app/Domain/` не вводился: §10 даёт иную,
уже опробованную задачами T-003…T-008 раскладку (`app/Enums`, `app/Models`
на месте), плодить параллельную структуру без указания ТЗ — хуже.

### Обязательство T-004 выполнено: isTerminal() читает конфиг

`OrderStatus::isTerminal()` переведён с захардкоженного набора на чтение
`config('marketplace.terminal_statuses')` (список заполняется строковыми
значениями case'ов enum'а). Способ — метод enum'а читает `config()`
напрямую, без промежуточного helper-класса: это Laravel-идиома, вызов
один, а indirection через отдельный класс ничего не добавляет, кроме
лишней сущности. Поведение сохранено (по умолчанию терминальны
`delivered`/`cancelled`), тест T-004 переведён с чистого PHPUnit на
`Tests\TestCase` (нужен контейнер для `config()`) и дополнен проверками
связки: смена конфига меняет `isTerminal()`, посторонние строки конфига
не опознаются как статусы (строгий `in_array`). Одно место истины —
конфиг; правило Q35 меняется без правки кода (риск R-2).

### Заглушки: явный отказ, а не фиктивный успех

`SnapshotVersionComparator::isNewer()`, `Money::subtotal()`,
`HistoryBuilder::{factsFromSnapshot,rollbackFact}()`,
`NotificationPolicy::allows()` — компилируемые типизированные скелеты,
каждый метод бросает `LogicException` с номером задачи-владельца
(T-022/T-023/T-030/T-031). Никакая заглушка не возвращает значение,
изображающее успешную бизнес-операцию (правило этапа 2); скелетные тесты
фиксируют именно бросание. Парсер JSON (сырое тело → DTO) сознательно
не создаётся — это задача T-021 целиком; T-009 даёт только типизированную
форму результата и исключения.

### Дискриминатор MalformedPayload — enum PayloadIssue

Ошибки тела покрывают два разных HTTP-кода: формат → 400 (`invalid_json`,
`event_id_mismatch`, FR-WH-05), структура → 422 (`invalid_envelope`,
`invalid_snapshot`, FR-WH-06/08). Вместо иерархии подклассов `MalformedPayload`
несёт типизированный enum `App\Enums\PayloadIssue` — match-дружелюбный
дискриминатор для HTTP-маппинга T-010/T-025. Enum кодовый (без колонки
БД): невалидные тела в журнал не попадают (FR-ORD-08). Сообщения всех
исключений — без секрета/подписи/тела (NFR-04). Для 401-семейства
(InvalidSignature, StaleTimestamp) контракт зафиксирован в PHPDoc базы
`WebhookException`: тело HTTP-ответа 401 едино для обеих причин, а
различающиеся дефолтные `getMessage()` предназначены только для логов
(наружу не отдаются) — маршрут для T-010/T-025 задокументирован явно,
чтобы единообразие 401 не держалось на негласной дисциплине.

## Задача 010. Скелет обработки вебхука

### Поток: маршрут → middleware → контроллер → Action → маппер

Структура вызовов — по §10 ТЗ: `POST /api/webhooks/marketplace`
(`routes/api.php`, api-маршрутизация включена в `bootstrap/app.php`
вручную, без `install:api`/Sanctum — FR-WH-01) →
`VerifyMarketplaceSignature` (шаги 2–4 §7) → тонкий
`MarketplaceWebhookController` (извлекает контекст доставки в DTO
`App\Data\IncomingWebhook`: X-Webhook-Id, timestamp, сырое тело) →
`App\Actions\Webhooks\ProcessMarketplaceEvent::handle()` (шаги 5–14 §7,
порядок зафиксирован приватными методами-шагами с заглушками
LogicException по задачам-владельцам) → `WebhookProcessingResult` →
`WebhookResponseMapper::fromResult()` (200 `{"status": …}`). Транзакционная
логика изолирована от HTTP: Action не принимает Request и не знает про
ответы; контроллер не содержит бизнес-логики. api-группа фреймворка
(без `install:api`) содержит только SubstituteBindings — CSRF и throttle
на маршрут не попадают (FR-WH-11, Q32), что подтверждено HTTP-тестом
с `Accept: text/html` (JSON остаётся — FR-API-09).

### Рендер исключений — одна точка, а не контроллер

`WebhookException` (InvalidSignature/StaleTimestamp из middleware,
MalformedPayload из Action) рендерится через
`$exceptions->render()` в `bootstrap/app.php`, а не try/catch
в контроллере: исключения middleware не проходят через контроллер,
а контракт тел ответов один для обоих источников. Единый маппер —
`App\Http\Responses\WebhookResponseMapper` (T-025 разовьёт его кодами
413/503).

### Заглушка HMAC: LogicException (T-024), а не фиктивный 401

Шаги 2–3 §7 реализованы сразу (формат трёх обязательных заголовков,
окно ±tolerance с границей — FR-WH-02/03 полностью специфицированы
и не пересекаются с криптографией T-024). Сверка HMAC (шаг 4) — явная
заглушка: бросает `LogicException('…(задача T-024)')`, т.е. HTTP 500.
Альтернатива «всегда InvalidSignature → 401» отклонена: 401 означал бы
ложное утверждение о недействительной подписи непроверенного запроса;
500 честнее («не готово, повторите») и семантически верно для MarketHub —
повторная доставка. Заглушка fail closed: до T-024 ни один запрос не
проходит к контроллеру (тест фиксирует недостижимость `$next`),
фиктивный `200 processed` исключён (правило этапа 2 и «Готово, когда»
задачи). Регистр hex в формате допускается любой (FR-WH-04 нормализует
при сравнении — T-024); префикс `sha256=` — строго нижний регистр.

### Тела ошибок: единый 401 и статичные 400/422

ТЗ форму ошибочных тел не задаёт (только «JSON, без payload и внутренних
ошибок»); фиксируется форма
`{"error":{"code":"<машины>","message":"<статичный русский>"}}`:

| Источник | Код | code |
|---|---|---|
| InvalidSignature, StaleTimestamp | 401 | `unauthorized` (единый, NFR-04) |
| MalformedPayload invalid_json / event_id_mismatch | 400 | код PayloadIssue |
| MalformedPayload invalid_envelope / invalid_snapshot | 422 | код PayloadIssue |
| 413 (1 MiB), 503 (lock) | — | добавят T-025/T-027 |

Тексты сообщений — статические константы маппера: `getMessage()`
исключений наружу не отдаётся (контракт T-009), детали валидации от
парсера T-021 (пути полей) останутся в логах, а не в ответах. Тексты
маппера и defaultMessage() исключений — независимые источники по
замыслу (первые стабильны для клиента, вторые — для логов). Ветка
default маппера для неизвестного подкласса WebhookException бросает
LogicException, а не отдаёт молча 401: забытая ветка (413/503 у

неповторяемым 401.

### Словари результатов: applied→processed, duplicate только в HTTP

rejected) — HTTP-словарь FR-WH-10; `fromOutcome(EventOutcome)` переводит
журнальный исход в HTTP (`applied` → `processed`), `duplicate` из БД
не переводится (FR-ORD-01/08: это ответ повторной доставке, исход записи
не заменяется). Маппинг покрыт unit-тестом, включая недостижимость
`duplicate` через `fromOutcome`.

## Задача 012. Скелет уведомлений и очереди

### Job: скалярный id, политика попыток из конфига, afterCommit

`SendOrderNotification` принимает **int $notificationId**, а не модель:
тело письма строится по ТЕКУЩЕМУ состоянию заказа (§6.5), поэтому запись
обязана загружаться в handle() заново; сериализованная в момент dispatch
модель создавала бы иллюзию актуальности, а `SerializesModels` под
капотом всё равно восстановил бы её по ключу — скаляр честнее. Свойства:
`$tries` = `notifications.max_attempts` (5, фиксируется в конструкторе —
только конструктор выполняется в контексте приложения при dispatch);
`backoff()` — метод (10/60/300/900 с читаются конфигом в момент повтора,
воркер всегда видит актуальные значения); `afterCommit = true` —
назначается в конструкторе, потому что свойство в трейте `Queueable`
объявлено без типа и дефолта (bool|null), а переобъявление в классе
несовместимо по типизации (fatal при композиции). Connection/queue не переопределяются:
единственная очередь проекта — default redis (§5.2), именованных
очередей ТЗ не вводит. handle(): шаг 1 §7 (загрузка; не-pending →
тихий выход) — честный, это идемпотентность повторной постановки
(sweeper + первичный dispatch сосуществуют безопасно); шаги 2–5 —
приватные методы-заглушки `LogicException('T-034')` с PHPDoc-ссылками
на T-031 (политика в шаге 3) и T-033 (тексты в шаге 5) — по образцу
`ProcessMarketplaceEvent` (T-010). `failed()` не вводится: судьба
записи при исчерпании попыток — решение T-034.

### Mailable'ы: честные темы, каркасы тел, отправитель из конфига

Темы трёх писем реализованы **честно** — это подстановка `number`,
а не бизнес-логика: `Заказ №{number} оплачен/передан в доставку/
отменён`, «№» — U+2116 (проверено тестом на реальный символ и
отсутствие суррогатов). Тела — blade-каркасы `resources/views/mail/
order-*.blade.php` (text-only): приветствие и факт статуса честные,
блоки состава/сумм/трека/причины — комментарии-заглушки с пометкой
T-033; до T-033/T-034 письма физически не отправляются, поэтому
фиктивного содержимого вьюхи не рендерят. Конструктор — только
`Order`: письмо целиком строится из текущего состояния заказа,
уведомление (`OrderNotification`) телу письма не нужно — его состояние
ведёт Job (T-034), получателя он же задаёт через `Mail::to`.
Отправитель не дублируется в Mailable'ах: глобальный `config/mail.php`
уже читает `MAIL_FROM_ADDRESS`/`MAIL_FROM_NAME`
(`no-reply@shop.local` / «Магазин», Q27) — единый источник истины.

### Dedupe-ключ: единая точка формата, фабрика переведена на неё

`App\Support\NotificationDedupeKey::for(type, orderId, tracking?)` —
чистая функция FR-MAIL-02 (`{order_id}:{type}`, для shipped —
`{order_id}:shipped:{tracking}`), реализована честно и покрыта unit-
тестами. `OrderNotificationFactory` (T-006) имел собственную private-
копию формата — переведена на общий класс (поведение сохранено, в т.ч.
пустой хвост для shipped без трека — нестандартная комбинация,
закрываемая skip-веткой FR-MAIL-08): устранено дублирование источника
правды без смены поведения.

### Переходы статусов: карта-данные на enum'е

Допустимые переходы `NotificationStatus` формализованы константой
`TRANSITIONS` + `canTransitionTo()` (полная матрица 5×5 покрыта
тестом): `pending → sending|skipped`, `sending → sent|skipped|failed|
pending`, `sent/skipped/failed` — терминальные. Обоснования:
`pending → skipped` — предотправочные проверки идут ДО захвата
(§7: шаг 3 раньше шага 4: политика, email, shipment);
`sending → skipped` — коллизия dedupe-ключа может вскрыться в окне
захвата (FR-MAIL-02: duplicate_tracking); `sending → pending` —
временная ошибка SMTP с attempts++ и backoff (FR-MAIL-05, не
«pending→pending»: попытка всегда проходит через захват);
`pending → sent/failed` запрещены — попытка невозможна мимо захвата.
Зависший `sending` не переотправляется (Q25) — sweeper его не ищет.

### Команды планировщика: честные сейчас

- **`notifications:sweep`** (FR-MAIL-06) — ре-постановка pending-записей
  старше `sweep_after_seconds` по `updated_at` (граница включительно:
  возраст порога достигнут — переставляем): метку обновляет любая
  попытка, поэтому письмо, уже перепланированное очередью с backoff,
  sweeper повторно не дёргает; дубликаты постановки безопасны по
  построению job (шаг 1 + атомарный захват FR-MAIL-04). Вызов Job-
  скелета — осознанно (задание: повторная постановка допустима).
- **`webhooks:prune`** (Q20) — честное удаление по `received_at`
  строго старше `events_retention_days` (90) — хранить полные дни
  хранения, поэтому граница исключительно; осознанное отличие от
  sweeper-семантики «достиг порога — действуй». Независимо от
  outcome; батчи `chunkById(1000)` с построчным delete
  и типизированным счётчиком (возврат bulk-delete у билдера
  в PHPStan — mixed). Возраст от `received_at`, а не от
  `last_received_at`: повторные доставки не продлевают срок
  хранения сырых тел — сырой payload нужен для разбора инцидентов
  ограниченное время.
- **Расписание**: sweeper — `everyMinute()` + `withoutOverlapping()`
  (дословно FR-MAIL-06); prune — `daily()` (00:00) + withoutOverlapping:
  событие можно удалить в любой момент после 90 дней, суточного
  запуска достаточно, нагрузка на БД минимальна (§5.3 не задаёт
  частоту; выбор закреплён тестом расписания).

`docs/operations.md` пока не существует (появится в T-035/T-045 по
плану T-014) — операционные подробности команд (ручная процедура для
зависших sending, запуск вручную) фиксируются здесь и перейдут туда.

### Остаток

`NotificationPolicy` не расширялся: сигнатура `allows(type,
currentStatus)` из T-009 уже покрывает матрицу §6.5, реализация —
T-031. Логирование sweeper/prune (NFR-06) — минимальный info-вывод
команд; структурированные логи появятся вместе с реальной обработкой
(T-034/T-035). Mail::fake/Queue::fake — стандарт тестов, реального
SMTP в тестах нет.

Заметка для T-034 (из ревью T-012): скелет job падает до записи
в БД, поэтому `updated_at` pending-записи не двигается и sweeper
переставляет её каждую минуту (постановки копятся в failed_jobs).
Боевого источника pending пока нет (outbox создаёт T-032), но к T-034
нужно либо ограничить sweeper условием `attempts < max_attempts`,
либо зафиксировать контракт «каждая попытка обновляет `updated_at`»
(тогда sweeper сам отступает на sweep_after_seconds после попытки).

## Задача 014. Инфраструктурный скелет качества и документации

### `composer check`: состав и порядок

`composer check` = `pint --test` → PHPStan (Larastan level 10) →
PHPUnit (Paratest, `artisan test -p`) → `vue-tsc --noEmit` — порядок
§5.1/NFR-15 ТЗ, тот же состав зафиксирован для CI в T-044. Решения:

- **Pint в режиме `--test`** (`pint-show`), не автофикс: единая команда
  качества обязана быть проверкой — она не может молча править файлы;
  автофикс остаётся в `back`/`min`/`max`.
- **PHPUnit через Paratest** (`@tests`), как в `max`: одна и та же
  тестовая конфигурация везде; DDL-особенность Paratest уже учтена
  правилом T-008. Скрипт `check` — цепочка над существующими
  `pint-show`/`phpstan`/`tests`/`tsc`, `min`/`max`/`back`/`front`
  не менялись.
- **`vite build` — отдельным скриптом `composer build`** (обёртка

## Задача 015. Тестовые помощники подписанных вебхуков

### Механика байт-в-байт POST

Тело доставляется через `call('POST', $uri, [], [], [], $server, $content)`
седьмым аргументом-строкой: он попадает в `SymfonyRequest::create()`
как есть — без перекодировки, включая финальный `\n` примеров.
`post()`/`postJson()` не годятся: массив кодируется заново, JSON
пересериализуется — байты меняются, подпись расходится (§3.1, R-1).
Заголовки идут server-массивом (`HTTP_*` + `CONTENT_TYPE`), как
в тестах T-010. Трейт `Tests\Support\PostsSignedWebhooks`
(`postSignedWebhook()`) — единственная точка этой механики для
будущих красных HTTP-тестов T-016–019. Байтовость доставки покрыта
тестом через runtime echo-маршрут (`getContent()` как есть) —
проверка не зависит от кода обработки вебхука.

### Принцип: сырые примеры — как есть, мутанты — пересериализация

Два честных режима, раздельных по назначению:

- **Сырые примеры** (`MarketplaceExamples::raw('order-paid')`) —
  `file_get_contents` от `base_path('task/examples/…')`, байт в байт,
  без json_decode/нормализации; подписываются и отправляются как есть.
  Папка `task/` не изменяется (инвариант задачи и §2 ТЗ).
- **Мутанты** (`MutatedWebhookBody`) — неизвестный `type`/`status`,
  управляемый `data.order.updated_at` — строятся неизбежной
  пересериализацией (json_decode → мутация → json_encode c
  `JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES` — кодировка как
  в примерах MarketHub). Мутант по построению **не** обязан совпадать
  с примером байт в байт (и не совпадает: у примеров есть финальный
  `\n`, у мутантов его нет) — это отдельный документ, подписываемый
  по собственным байтам. Смешение режимов не допускается: сценарии
  «пересериализация ломает подпись» (S-13) тестируются только на
  сырых примерах с честной подписью по исходным байтам.

### Эталонная самопроверка и детерминированные дефолты

`Tests\Support\WebhookSignature` повторяет формулу send-event.php
дословно (`hash_hmac('sha256', $timestamp . '.' . $rawBody, $secret)`,
hex нижний регистр, заголовок `sha256=<hex>`) и существует отдельно
от будущего `App\Support\MarketplaceSignature` (T-024): тесты обязаны
подписывать независимо от кода приложения. Самопроверка — exact-match
по `signature-example.md` (тело 765 байт, timestamp 1792577149, секрет
`whsec_test_5f1d8c2a9b` → `4d4f2d50…cb163f7`). Дефолты `SignedWebhook`:
timestamp — из замороженного `CarbonImmutable::now()` (паттерн `travelTo`
по §11 ТЗ), секрет — `config('marketplace.webhook_secret')`; пустой
секрет — `LogicException` (fail fast инфраструктуры: подпись пустым
ключом бессмысленна), эталонный timestamp всегда задаётся явно.
`X-Webhook-Id` берётся из `body.id` как в send-event.php; тело без
читаемого id — заголовок опускается, негативные варианты (S-13/S-15/S-16)
задаются `withHeader()`/`withoutHeader()` (сопоставление имени — без
учёта регистра, чтобы иное написание не давало молчаливого no-op).
`server()` задаёт и `CONTENT_LENGTH` фактического размера тела:
Symfony не синтезирует его из `$content`, а реальный запрос его несёт —
важно для проверок лимита 1 MiB (FR-WH-12, T-017). Тесты хелперов
зелёные по требованию задачи; фактическое поведение настоящего
маршрута зафиксировано как «валидная подпись проходит заголовки/окно
и упирается в заглушку HMAC T-024» (500, не 401).

### Решение: правила переходов Q35 — не на уровне OrderStatus

Проверено по ТЗ §6.2 FR-ORD-09: запрет `delivered → cancelled`,

статуса. Отдельного unit-API допустимости переходов у `OrderStatus`
в ТЗ нет (§6.2 явно: ранг — только для сортировки истории), поэтому
в 016 он не вводится: S-29…S-31 закрываются интеграционными тестами

cancelled=4); смежная граница истории «переход в терминальный —

### Решение: подпись — разметка уровней

Серверной функции сверки подписи ещё нет (T-024), а HTTP-прогон
валидного запроса упирается не только в HMAC, но и в заглушки
процессора событий (T-021+) — такой красный тест не позеленел бы от
одной реализации T-024. Поэтому будущее поведение HMAC зафиксировано
на уровне middleware (`handle()` + флаг достижения `$next`): падение
локализовано ровно в заглушке T-024 и тесты становятся зелёными
строго с T-024 независимо от остальных задач. Формат заголовка и
окно времени уже реализованы (T-010) и покрыты: их дублирование

### Допущение: статусный факт при null «родного» поля — fallback на updated_at

FR-HIS-01 формулирует fallback «родное поле null → updated_at» для

Зафиксировано тестами `test_paid_snapshot_without_paid_at_falls_back_
to_updated_at` и `test_cancelled_snapshot_without_cancelled_at_falls_
back_to_updated_at`; T-030 реализует без переоткрытия спора.

### Решения

- **Конкурирующая доставка — последовательно.** Честный параллельный

  за T-019.
- **503-тест без Redis.** Тест занимает тот же лок, что займёт

### Решение: транзакционность outbox — три теста + DatabaseMigrations

Три грани FR-MAIL-01 разделены по наблюдаемости:

1. **Атомарность (rollback)** — тест открывает свою транзакцию
   (`DB::beginTransaction` поверх RefreshDatabase), постит вебхук,
   фиксирует наличие заказа+outbox+журнала и откатывает транзакцию:
   все три таблицы пусты. Создание outbox вне транзакции применения
   оставило бы «сироту» — тест упал бы.
2. **Постановка есть, письма в запросе нет** — `Queue::fake()`:
   `processed` → ровно один `SendOrderNotification` с id созданной
   записи; `Mail::fake()` + `assertNothingSent` — письмо уходит только
   через очередь (NFR-01: никаких сетевых вызовов в HTTP-запросе).
   Отрицательная ветка: 422 до применения — постановки нет.
3. **«До commit» — отдельный набор `MarketplaceWebhookOutboxCommitTest`
   на `DatabaseMigrations`** (а не RefreshDatabase): у `QueueFake::push`
   нет транзакционной осведомлённости (отложенность живёт в
   `Illuminate\Queue\Queue::enqueueUsing` → `db.transactions`, фейк
   пишет сразу — «не запушено до commit» фейком проверить нельзя),
   а RefreshDatabase никогда не коммитит корневую транзакцию —
   afterCommit-колбэки внутри теста не исполнить. С DatabaseMigrations
   транзакция теста корневая: реальный `database` queue-драйвер, внутри
   `jobs` пусто, после `DB::transaction(...)` — ровно одна строка
   с payload `SendOrderNotification`. Это второе осознанное исключение
   из «DB-тесты = RefreshDatabase» (после DDL-правила T-008): трейт
   стандартный, per-process БД Paratest работает; цена — один
   дополнительный `migrate:fresh` на процесс.

### Решение: retry-контракты и заметка sweeper+attempts (T-034)

Временная ошибка SMTP моделируется настоящим transport'ом
(`mail.manager->extend`, Symfony `TransportException` — каноническая
временная ошибка транспорта), `Mail::fake()` для успеха. В тестах
временной ошибки `handle()` вызывается под `catch (Throwable)`:
политика задания (погасить и записать либо перебросить в очередь
для повтора по backoff) свободна, пиннится состояние записи —
единственный наблюдаемый контракт FR-MAIL-05. `last_error` в
`failed` пиннится непустым (колонка существует для диагностики,
factory `failed()` так заполняет). Тест «pending с attempts=5»
сознательно НЕ добавлялся: по FR-MAIL-05 пятая ошибка обязана
приводить к `failed`, а переход `pending → failed` запрещён картой
переходов T-012 — достижимый краш-остаток после падения воркера
в критическом окне — `sending`, чья непереотправка уже покрыта
зелёными тестами; гарантия «≤ 5 попыток» держится на failed-границе
(тест «4 → 5 → failed») + терминальности `failed` для sweeper.
Выбор механизма из заметки T-012 (фильтр sweeper по attempts <
max либо «каждая попытка обновляет updated_at») остаётся за T-034 —
оба варианта совместимы с тестами задачи.

### Флак демо-сида: `Faker\Generator::__destruct()` подменяет mt_srand

Приоритетная диагностика из T-018/T-019. Симптом: `test_rerun_
rebuilds_identical_dataset` падал только в полных прогонах (случайный
порядок тестов), fingerprint второго сида всегда канонический,
первого — произвольный «другой мир» (ни одного совпадения значений
после точки разрыва — по маркерам mt это подмена состояния, а не
сдвиг последовательности). Механизм: `Faker\Generator::__destruct()`
вызывает `seed()` без аргумента → глобальный `mt_srand()` со
случайным сидом; Laravel создаёт Faker-генератор синглтоном в
контейнере каждого теста (helpers `fake()` — `Faker\Generator:locale`,
фабрики — `Faker\Generator`), при пересоздании приложения старый
генератор становится мусором, и GC зовёт его деструктор в
произвольной точке следующего теста (бэктрейс детектора — прямо
внутри `Factory::create()` цикла сида). mt-состояние у Faker одно на
процесс, поэтому фиксированный `FAKER_SEED` терялся посреди цикла.

Решение: **один Faker-генератор на процесс** — статический инстанс
в `Tests\TestCase::setUp` + `instance()`-биндинги обоих ключей
(`Faker\Generator` и `Faker\Generator:en_US`): деструкторов между
тестами нет, подмена состояния исчезает, генерация значениями не
меняется (mt-последовательность и так была сквозной на процесс).
Сайд-эффект — общий `unique()`-пул на процесс: единственный
потребитель `fake()->unique()` — email `UserFactory`, один вызов на
сьют, влияния нет.

### Трактовки спорных мест протокола (по тексту ТЗ/§7)

- **Порядок шагов 6→7**: несовпадение `X-Webhook-Id`/`body.id` — 400
  `event_id_mismatch` ДО проверки конверта; отсутствующий или
  не-строчный `body.id` совпасть не может → тоже 400 (не 422).
- **Валидный JSON не-объект** (`null`, `"hello"`, `123`) — 422
  `invalid_envelope`, не 400: JSON корректен (FR-WH-05 о «невалидном
  JSON»), конверту неоткуда взять обязательные поля (FR-WH-06).
- **ISO 8601 «со смещением»** — `±HH:MM` **или `Z`** (нулевое
  смещение), дробные секунды допустимы (момент однозначен). Настенное
  время без offset — 422 (FR-ORD-03). День сверки `checkdate()`:
  Carbon молча прокатывает `2026-02-29` → `2026-03-01` (проверено).
  «Перелив» времени (ревью r2, P3): секунда `:60` (нотация leap
  second ISO 8601) и `24:00:00` (запись конца дня) принимаются и
  нормализуются Carbon к следующей минуте/дню — момент однозначен
  (проверено прогоном); час ≥ 25, минута ≥ 60, месяц и offset вне
  диапазона — отказ Carbon. Строгий запрет `:60`/`24:00` отвергал бы
  корректные ISO 8601-формы — не вводится.
- **Непустые строки** — для идентификаторов и смысловых полей:
  `order.id`, `number`, `customer.email`, `customer.name`,
  `items[].{sku,name}`, `shipment.{carrier,tracking_number,
  tracking_url}`. Nullable-поля (`customer.phone`, `cancel_reason`) —
  `null` либо любая строка, включая пустую: парсер проверяет только
  тип, бизнес-смысл (письма, БД) — ниже по стеку.
- **`order.status` — строка без требования непустоты** (ревью r2,
  P2): шаг 9 §7 требует от status именно «строку», в отличие от
  «непустых id/type» шага 7; FR-WH-07 направляет в `ignored` любую
  строку вне enum. Пустая и пробельная строка → ветка `ignored`
  (снимок не валидируется), 422 — только не-строка или отсутствие
  поля (S-17). Непустота для status означала бы 8 бесполезных
  повторов MarketHub на глитч-событии — ловушка T9.
- **Формат email не проверяется** (только непустая строка):
  невалидный адрес — `skipped (invalid_recipient)` письма (FR-MAIL-07),
  а не отказ вебхука.
- **`items` — список, пустой допустим**: протокол не требует непустоты;
  каждый элемент — объект с обязательными полями.
- **Валюта `^[A-Z]{3}$` без списка** RUB/USD/EUR (FR-WH-08 явно),
  суммы `^-?\d+\.\d{2}$` — минус допустим формату любой суммы,
  включая `total`: отрицательный итог принимается, при расхождении
  с арифметикой — только warning (FR-WH-09). Во входных примерах
  отрицательных сумм нет; поведение следует букве формата FR-WH-08
  (вопрос поднимался прерванным ревью — подтверждён как не-находка
  ревью r2). `quantity` — строго целое ≥ 1 (строка `"3"` — неверный
  тип).
- **Ограничение json_decode (ревью r2, P3)**: PHP при assoc-разборе
  не различает JSON-объект `{"0":…}` и список `[…]` — непустой объект
  со сплошными числовыми ключами от нуля в `data`/`data.order`/

  (для неизвестного типа `data` — 422 вместо 200 ignored). Для
  реальных событий MarketHub недостижимо (ключи объектов протокола —
  строки); двойной разбор через stdClass не вводится — зафиксировано

## Задача 022. Money и расчёт subtotal

### Реализация: BigDecimal, без float и без молчаливого округления

`Money::subtotal($price, $quantity)` =
`(string) BigDecimal::of($price)->multipliedBy($quantity)->toScale(2)` —
точное произведение произвольной разрядности (99 999 999.99 × 99 =
9 899 999 999.01 на границе DECIMAL(12,2) §6.3 — float давал
9899999999.009999… и терял копейки), результат — строка ровно с двумя
знаками (FR-API-06, §6.5). Формат входа — предпосылка источников
(парсер — `^-?\d+\.\d{2}$` FR-WH-08, БД — каст decimal:2), повторная
валидация в хелпере не дублируется: мусорный вход громко падает
NumberFormatException от `BigDecimal::of`, а `toScale(2)` с режимом по
умолчанию (UNNECESSARY) бросает RoundingNecessaryException вместо
молчаливого округления — фиктивных сумм метод не возвращает.

Тип параметра — `string`, а не унаследованный от заглушки
`non-empty-string`: метод не проверяет непустоту сам, а доказать
non-empty у обоих источников нельзя без запрещённых PHPStan'ом
assert()/`@var`-оверрайдов (`amount()` парсера возвращает `string` после
preg_match). Контракт — в докблоке (формат + отказ на мусоре).

### Warning-арифметика парсера унифицирована с Money

Решение по вопросу задачи: **унифицировать**. `warnOnTotalMismatch`
считает `Σ Money::subtotal(price, qty) + delivery − discount` вместо
локального `BigDecimal::of(price)->multipliedBy(qty)` — принцип аудита
P3.7 (дедупликация арифметики) распространён и на парсер, формула
читается дословно по FR-WH-09. Поведение T-021 не изменилось: Money
точен, round-trip строка↔BigDecimal без потерь, контекст warning
байт-в-байт тот же (`expected_total` = `(string) $expected->toScale(2)`,

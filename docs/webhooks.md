## Эндпоинт

`POST /api/webhooks/marketplace` — `routes/api.php` (api-маршрутизация
включена вручную, без `install:api`/Sanctum, FR-WH-01). Для маршрута
отключены CSRF и throttle; все ответы `api/*` — JSON независимо от
заголовка `Accept` (FR-WH-11, FR-API-09). Лимит тела — 1 MiB (FR-WH-12,
раздел «Лимит тела»).

## Заголовки аутентификации

| Заголовок | Формат |
|---|---|
| `X-Webhook-Id` | идентификатор события (совпадает с `body.id`, иначе 400) |
| `X-Webhook-Timestamp` | целое число, Unix-секунды |
| `X-Webhook-Signature` | `sha256=<64 hex-символа>` (регистр нормализуется к нижнему) |

Окно времени: `abs(now − timestamp) ≤ MARKETPLACE_WEBHOOK_TOLERANCE`
(по умолчанию 300 с, в обе стороны); вне окна — 401 (FR-WH-03).

## Подпись

Подпись считается по **сырым байтам тела** — `"{timestamp}." . $request->getContent()`:

```text
signature = hash_hmac('sha256', $timestamp . '.' . rawBody, secret)
```

- тело **не нормализуется и не пересериализуется** до проверки: кириллица
  неэкранирована, `/` может быть экранирован, финальный `\n` участвует
  в подписи (примеры `task/examples/order-*.json` заканчиваются переводом
  строки — `send-event.php` подписывает файл «как есть»);
- сравнение — `hash_equals` (NFR-04);
- секрет — `MARKETPLACE_WEBHOOK_SECRET` (читается только через
  `config('marketplace.webhook_secret')`); **пустое значение — fail
  closed**: все вебхуки отклоняются с 401 (Q11);
- 401 одинаков для всех причин отказа аутентификации (нет заголовков,
  неверный формат, окно, подпись) — ответ не раскрывает, какая проверка
  не прошла (NFR-04).

> **Статус реализации.** Заголовки, окно времени и сверка HMAC
> реализованы в middleware `VerifyMarketplaceSignature` (шаги 2–4 §7,
> T-010/T-024): подписанный запрос проходит аутентификацию и доходит
> до контроллера. Лимит тела 1 MiB проверяет более ранний middleware
> `LimitMarketplaceWebhookBody` (шаг 1 §7, T-025) — см. раздел
> «Лимит тела». Разбор тела (шаги 5–11 §7) —
> `App\Support\MarketplaceEventParser` (T-021): невалидный JSON/несовпадение
> ID → 400 `invalid_json`/`event_id_mismatch`, неверный конверт/снимок →
> 422 `invalid_envelope`/`invalid_snapshot` (правила — раздел
> «Правила приёма событий»); эти ответы наблюдаемы из HTTP с T-024.
> Журналирование и идемпотентность (шаги 8/10/13a §7) —
> `App\Actions\Webhooks\ProcessMarketplaceEvent` (T-026): исходы
> `ignored`/`duplicate` наблюдаемы из HTTP (см. раздел «Журнал событий
> и идемпотентность»). Блокировка заказа `order:{id}` с ожиданием и
> транзакция с `SELECT … FOR UPDATE` (шаги 12–13 §7) реализованы там же
> (T-027, раздел «Блокировки и конкурентность»): занятая блокировка
> отвечает 503. Применение снимка реализовано (T-028, раздел
> «Применение снимка заказа»): валидное событие известного типа
> применяется — 200 `processed`/`stale`; правило терминальных статусов
> Q35 (шаг 13d §7) — T-029: выход из `delivered`/`cancelled` —
> 200 `rejected`.
> Ручная проверка подписи доступна (см. раздел
> «Ручная отправка события»).

## Лимит тела

Ограничение — **1 MiB** (FR-WH-12): тело строго больше лимита → **413**
`payload_too_large`; ровно 1 MiB — допустимо.

В Sail веб-сервер — `php artisan serve`, nginx отсутствует, поэтому
лимит проверяет само приложение на самом раннем этапе — middleware
`LimitMarketplaceWebhookBody` (шаг 1 §7) **до** проверки заголовков
и подписи (`VerifyMarketplaceSignature`, шаги 2–4) и до любого
JSON-разбора (шаг 5): oversized-запрос отвечает 413 раньше 401/400/422.

Проверяются оба источника размера (FR-WH-12):

- заголовок `Content-Length` больше лимита — отказ до чтения тела
  (прикрывает случай, когда настройка PHP обрезала переданные байты
  и фактический размер уже не виден);
- фактический размер сырых байтов `getContent()` — при отсутствующем,
  заниженном или мусорном заголовке решение принимает он.

Значение — `config('marketplace.webhook_max_body_bytes')` (константа
протокола 1 MiB, env-переменной не имеет). Если позже добавляется
reverse proxy, тот должен иметь такой же или больший лимит и возвращать
совместимый ответ (FR-WH-12).

## Коды ответов

Реализованы `WebhookResponseMapper` (T-010/T-025); тела — JSON без
payload и внутренних деталей (FR-WH-10). Исключения вебхука
(вся иерархия `App\Exceptions\Webhook\WebhookException`) исключены из
репортинга (`ShouldntReport`, T-025): ожидаемые клиентские 401/400/422/413
и повторяемый 503 не пишут стектрейсы в логи; наблюдаемость этих веток —
warning-логи NFR-06 (T-026/T-027).

| Код | Тело | Когда |
|---|---|---|
| 200 | `{"status": "processed"}` | событие применено (T-028); при допустимой смене статуса создана outbox-запись и после commit поставлено задание отправки (T-032) |
| 200 | `{"status": "duplicate"}` | повторная доставка того же `event.id` (FR-ORD-01; T-026) |
| 200 | `{"status": "stale"}` | входящая версия не новее сохранённой (FR-ORD-02; T-028) |
| 200 | `{"status": "ignored"}` | неизвестный тип или статус (FR-WH-07; T-026) |
| 200 | `{"status": "rejected"}` | переход из терминального статуса (FR-ORD-09, Q35; T-029) |
| 401 | `{"error": {"code": "unauthorized", ...}}` | единый ответ для всех причин отказа аутентификации (T-024) |
| 400 | `{"error": {"code": "invalid_json" \| "event_id_mismatch", ...}}` | тело не JSON UTF-8; несовпадение `X-Webhook-Id` и `body.id` (FR-WH-05; разбор — `MarketplaceEventParser`, T-021) |
| 413 | `{"error": {"code": "payload_too_large", ...}}` | тело больше 1 MiB (FR-WH-12; `LimitMarketplaceWebhookBody`, T-025) |
| 422 | `{"error": {"code": "invalid_envelope" \| "invalid_snapshot", ...}}` | невалидный базовый конверт или снимок (FR-WH-06/08; валидация — `MarketplaceEventParser`, T-021) |
| 503 | `{"error": {"code": "temporarily_unavailable", ...}}` | блокировка заказа не получена за `order_lock_timeout` либо исчерпаны попытки транзакции при deadlock (FR-WH-10/FR-ORD-07) — повторяемый отказ без `Retry-After` (политика повтора — за MarketHub); реализовано T-027 |

> Исходы `duplicate` (включая повтор с изменённым телом) и `ignored`
> (неизвестный тип/статус) реализованы (T-026, раздел «Журнал событий
> и идемпотентность»); 503 — T-027 (раздел «Блокировки
> и конкурентность»); `processed`/`stale` — T-028, `rejected` —
> T-029 (раздел «Применение снимка заказа»).

## Журнал событий и идемпотентность

Реализовано в `App\Actions\Webhooks\ProcessMarketplaceEvent` (T-026,
шаги 8/10/13a §7, FR-ORD-01/08). Каждое событие с валидной подписью
и валидным базовым конвертом фиксируется в таблице `webhook_events`
одной строкой на `event.id` (PK):

| Поле | Значение |
|---|---|
| `id` | `event.id` из конверта |
| `type` | тип события (в т.ч. неизвестный — дословно) |
| `order_id` | `data.order.id` после структурных проверок; NULL для неизвестного типа |
| `signature_timestamp` | `X-Webhook-Timestamp` первой доставки |
| `payload` | сырое тело байт в байт (включая финальный `\n`) |
| `payload_sha256` | SHA-256 от тех же сырых байтов |
| `outcome` | `applied` \| `stale` \| `ignored` \| `rejected` (FR-ORD-08) |
| `reject_reason` | причина отказа: `terminal_status` для `rejected` (шаг 13d, T-029); NULL у прочих исходов |
| `deliveries` | количество доставок, начиная с 1 |
| `received_at` / `last_received_at` | время первой приёмки / последней повторной доставки |
| `processed_at` | время завершения обработки: для `ignored` — момент вставки; для применяемых — финализация шагов 13c/13d/13g вместе с фактическим исходом (`applied`/`stale`/`rejected`, T-028/T-029) |

Невалидный JSON, несовпадение ID, неверный конверт и некорректный
снимок известного статуса в журнал **не попадают** (4xx до вставки,
FR-ORD-08).

**Повторная доставка того же `event.id`** (новые timestamp/подпись,
в т.ч. параллельная, в т.ч. «после успеха»):

- снимок не применяется повторно; ответ **200 `duplicate`**;
- `deliveries++` и `last_received_at` — одним атомарным UPDATE;
- исходные `payload`/`payload_sha256`/`outcome`/`order_id`/
  `signature_timestamp`/`received_at` **не заменяются**: `duplicate` —
  только HTTP-ответ, исход записи журнала сохраняется (FR-ORD-08);
- если повтор пришёл **с другим телом** (хеш отличается) — это всё
  равно дубль: новое тело **не сохраняется**, пишется warning
  `duplicate_payload_mismatch` с контекстом `event_id`/`order_id`/
  `stored_payload_sha256`/`incoming_payload_sha256` — без содержимого
  payload (NFR-04/06).

**Границы транзакций** (FR-ORD-01): вставка события и применение
снимка — **одна** БД-транзакция (шаг 13 §7): сбой применения
откатывает и запись журнала — частичных эффектов не бывает.
Применение снимка реализовано (T-028, раздел ниже). Duplicate-ветка
выполняется в транзакции вызывающей ветки под той же блокировкой
заказа (шаг 12 §7 — до транзакции), но **не запускает** применение.
Ignored-ветки (шаги 8/10) живут в своих коротких транзакциях
**без** блокировки заказа — заказ не трогают.

**Warning-логи** (NFR-06): `unknown_type` (контекст `event_id`,
`type`), `unknown_status` (`event_id`, `order_id`),
`duplicate_payload_mismatch`, `terminal_status` (`event_id`,
`order_id`, `order_status`, `incoming_status` — шаг 13d, T-029) —
только идентификаторы, статусы и хеши, без тела, секрета, подписи
и персональных данных; значение неизвестного статуса доступно из
сохранённого payload журнала. Warning-логи блокировок — в разделе
«Блокировки и конкурентность».

## Блокировки и конкурентность

Реализовано в `App\Actions\Webhooks\ProcessMarketplaceEvent`
(T-027, FR-ORD-07; шаги 12–13 §7) — контур вокруг транзакции
применения события известного типа:

1. **Redis-lock `order:{order.id}`** — `Cache::lock()` c
   `order_lock_lease` (15 с, больше SMTP timeout — lock не истечёт
   под чужой длинной операцией) и ожиданием `block()` не дольше
   `order_lock_timeout` (3 с). Блокировка общая для вебхуков и
   отправки письма (FR-MAIL-03, T-034 возьмёт тот же ключ).
   Не получена → **503** `temporarily_unavailable` — повторяемый
   отказ: MarketHub обязан повторить доставку; заголовок
   `Retry-After` не отдаётся (ТЗ не требует, политика повтора — за
   маркетплейсом).
2. **Транзакция с `SELECT … FOR UPDATE`**: вся обработка — вставка
   журнала (13a), duplicate-ветка и применение (13b–13g) — одна
   транзакция (FR-ORD-01); строка заказа блокируется
   `Order::lockForUpdate()->find()` (13b; для первого снимка строки
   нет — блокировать нечего, гонку создания исключает Redis-lock).
   При конкурентной ошибке БД (deadlock 1213, lock wait timeout
   1205) Laravel повторяет транзакцию целиком до **3 попыток**
   (FR-ORD-07: `attempts: 3`); после исчерпания — 503
   (повторяемый), прочие ошибки БД — громкий 500 без маскировки.
3. **Освобождение в `finally`** — на все исходы контура, включая
   исключение заглушки применения и неудачу захвата (release без
   владения безопасен: драйвер сверяет owner-токен).

Сетевые вызовы (SMTP/HTTP) внутри контура запрещены (NFR-01: их нет
в запросе вебхука вообще; письмо идёт через outbox и очередь — outbox
создаётся в транзакции применения (T-032), отправку выполняет задание
очереди T-034). Бюджет запроса против дедлайна MarketHub 5 с
(FR-ORD-07) обеспечивается структурой, а не секундомером: ожидание
lock ≤ 3 с + три попытки транзакции; deadlock MySQL детектируется
мгновенно. Теоретический край: попытка может стоять на `FOR UPDATE`
до `innodb_lock_wait_timeout`, если строку держит процесс вне
контура (все писатели контура сериализованы Redis-lock —
реалистичность низкая); остаток честно отнесён к интеграционному
P1-плану (docs/testing.md).

**Warning-логи** (NFR-06): `order_lock_timeout` (контекст `event_id`,
`order_id`) и `transaction_retry_exhausted` (`event_id`, `order_id`) —
повторяемые отказы конкурентности; только идентификаторы и машинный
токен причины, без тела, секрета и подписи.

## Применение снимка заказа

Реализовано в `App\Actions\Webhooks\ProcessMarketplaceEvent`
(T-028, шаги 13c/13e/13g §7; FR-ORD-02/04/05/06) — внутри транзакции
журнала под блокировкой заказа (раздел выше).

**Версия и stale (13c, FR-ORD-02).** Версия заказа — кортеж
`(order.updated_at, event.created_at, event.id)`, сравнение —
моментами UTC (`SnapshotVersionComparator`, T-023). Первый снимок
(заказа нет) применяется всегда — заказ создаётся из любого статуса,
включая первым пришедший `order.paid`/`order.shipped` (FR-ORD-06).
Для существующего заказа применяется только **строго большая**
версия; равная или старая → **200 `stale`**: состояние заказа не
меняется, позиции не трогаются, письма не создаются, событие
фиксируется в журнале с `outcome=stale` и `processed_at` (FR-ORD-08).
При этом достоверные факты истории из устаревшего снимка принимаются
(FR-HIS-02) — см. раздел «История статусов».

**Терминальные статусы (13d, FR-ORD-09, допущение Q35; T-029).**
Если текущий статус заказа терминальный (`delivered`/`cancelled` —
`config('marketplace.terminal_statuses')`, единственное место
истины для `OrderStatus::isTerminal()`), а свежий снимок предлагает
**другой** статус — применение отклоняется: **200 `rejected`**,
заказ/позиции/история/письма не меняются, событие фиксируется
в журнале с `outcome=rejected`, `reject_reason=terminal_status`
и `processed_at`, warning в логе (контекст — event/order IDs и оба
статуса, NFR-06). Запрет охватывает и переходы между самими
терминальными статусами (`delivered → cancelled` и обратно) —
консервативное допущение Q35 (§16.2 ТЗ), не подтверждённое
документацией MarketHub; при разъяснениях достаточно поменять список
в конфиге (риск R-2). Снимок с **тем же** терминальным статусом
проходит дальше в 13e: обновление данных/причины допустимо (S-31);
уведомление при этом не создаётся — триггер 13f требует смены
статуса (T-032). Проверка идёт после 13c: устаревший снимок
при терминальном заказе отвечает `stale`, не `rejected` (порядок
шагов §7); повторная доставка отклонённого события — `duplicate`
с сохранением исходной записи журнала (13a раньше, FR-ORD-01).

**Полная перезапись (13e, FR-ORD-04/05).** Снимок MarketHub всегда
полный, применение перезаписывает **все** поля заказа, включая явные
`null`: shipment-тройка, `paid_at`, `cancelled_at`, `cancel_reason`,
`customer.phone` сбрасываются, если в снимке null. Статус берётся из
`order.status` снимка, а не из `type` события; откат статуса свежим
снимком допустим (кроме выхода из терминальных, 13d). Позиции
заменяются целиком (delete + insert в той же транзакции), порядок
снимка сохраняется как `position` 1..N. Вместе с применением в историю
записываются факты снимка и, при откате статуса, факт коррекции
(раздел «История статусов»). `customer_email` хранится как пришёл,
`customer_email_normalized` — `trim + lower`.

**Даты MarketHub и версия.** `placed_at` = `created_at` снимка,
`source_updated_at` = `updated_at` снимка; обе нормализуются в UTC
до записи (FR-ORD-03) и хранятся отдельно от системных
`created_at`/`updated_at` Eloquent (которые в API не используются).
Компоненты версии пишутся в `version_event_created_at` /
`version_event_id`; столбец `snapshot` хранит сырой `data.order`
как прислал MarketHub — включая поля, которых ещё нет в валидации
(«для отладки и совместимости при новых полях», §6.3 ТЗ).

## Outbox-уведомления (13f/14)

Реализовано в `App\Support\NotificationTrigger` (чистое правило
триггера) + запись и dispatch в `ProcessMarketplaceEvent`
(T-032, FR-MAIL-01/02; §6.5 A-22/A-28). `duplicate`, `stale`,
`ignored` и `rejected` до триггера не доходят — их ветки
заканчиваются раньше применения.

**Триггер.** Outbox-запись создаётся, только если применённый снимок
**действительно меняет** статус заказа на `paid`, `shipped` или
`cancelled`:

- **тип письма — из нового статуса заказа**, не из `event.type`
  (совпадение типа события и статуса ТЗ не вводит: `order.updated`
  со сменой на `paid` создаёт paid-письмо; `order.shipped` первым —
  только shipped-письмо, хотя факт `paid` и восстанавливается в
  истории по `paid_at`, A-22);
- **первый снимок** (создание заказа) со статусом paid/shipped/
  cancelled триггер проходит — смена «не существует → существует
  в статусе» полноправна (S-06/S-07);
- **тот же статус** (обновление полей, включая терминальный —
  S-31) — письма нет, смены нет;
- **откат статуса** (строгая убыль ранга `created=0, paid=1,
  shipped=2, delivered=3, cancelled=4` — та же механика, что у
  факта коррекции истории FR-HIS-03) — письмо-исправление
  не отправляется (Q28: коррекция `shipped → paid` меняет состояние
  и историю, но не запускает повторное письмо «оплачен», S-37);
  переход **в** терминальный (`shipped → cancelled`) откатом
  не является; переходы **из** терминальных до триггера не
  доходят (13d, T-029).

Матрица допустимости `NotificationPolicy` (T-031) при создании
**не** проверяется: тип триггера всегда совпадает с новым статусом,
а диагональ матрицы (`paid@paid`, `shipped@shipped`,
`cancelled@cancelled`) всегда допустима — политика нужна на момент
**отправки**, когда статус мог смениться (FR-MAIL-03, S-10 → T-034).

**Запись.** `order_notifications`: `status=pending`, `attempts=0`,
`type`, `order_id`, `source_event_id` (событие-триггер), `dedupe_key`
по FR-MAIL-02 — `NotificationDedupeKey::for()`: `{order_id}:paid`,
`{order_id}:cancelled`, `{order_id}:shipped:{tracking_number}`
(трек-номер **события-триггера**; сверка ключа с треком текущего
снимка перед отправкой — T-034). `recipient`/`subject` не
заполняются: тело письма строится по текущему состоянию заказа на
момент отправки (§6.5). Запись создаётся в **той же транзакции**,
что и применение снимка (FR-MAIL-01): откат уносит заказ, outbox
и журнал вместе.

**Дедупликация.** `UNIQUE(dedupe_key)` (nullable): конфликт вставки
— точный перехват `UniqueConstraintViolationException` по образцу
журнала (T-026; `insertOrIgnore` глотал бы прочие ошибки строки) —
молчаливый пропуск «INSERT IGNORE: дубль → письмо не создаётся»
(FR-MAIL-02): повторный `shipped` с тем же треком после коррекции
второго письма не порождает (S-11), с другим треком — создаёт
(свободный ключ). Применение снимка дубль ключа не ломает — заказ
обновляется, событие `applied`. Освобождение ключа (`dedupe_key =
NULL`) для пропущенного `skipped`-письма — операция задания отправки
(FR-MAIL-03, T-034); схема это разрешает (NULL в unique-индексе
MySQL не конфликтует, миграция T-003).

**Dispatch после commit (шаг 14 §7).** `SendOrderNotification::dispatch(id)`
регистрируется через `DB::afterCommit` внутри транзакции применения:
фактическая постановка происходит после commit создавшей запись
транзакции (в бою — корневой; менеджер транзакций БД не исполняет
колбэк на откат — задание не увидит несуществующую запись). Постановка
изолирована от ответа: неудачная постановка (Redis недоступен) —
warning `dispatch_failed` и **200 `processed`**, запись остаётся
`pending` — её переставит sweeper (FR-MAIL-06, T-035). Идентификатор
задания — скалярный `notificationId` (тело письма — по текущему
состоянию, запись перезагружается в `handle()`); у задания
дополнительно `afterCommit = true` — защита от прямой постановки
внутри чужой транзакции. Механика отправки (шаги 2–5 задания) —
T-034. Тексты писем реализованы (T-033): три синхронных Mailable
`Order{Paid,Shipped,Cancelled}Mail` с телами
`resources/views/mail/order-*.blade.php` — plain text UTF-8, темы и
строки состава/сумм дословно §6.5 (стоимость позиции —
`Money::subtotal`, суммы — как в снимке + код валюты, A-26);
`shipped` — служба/трек/ссылка из текущего состояния; `cancelled` —
причина или «Причина не указана» (Q26) и «Деньги вернутся в течение
N дней.» только при `paid_at ≠ null` (N = `notifications.refund_days`).
Задание отправки (T-034) передаёт им `Order` и задаёт получателя
`Mail::to(...)` из текущего состояния заказа.

## История статусов

Реализовано в `App\Support\HistoryBuilder` (чистые факты из снимка)
+ идемпотентная запись в `ProcessMarketplaceEvent` (T-030,
FR-HIS-01…04) — таблица `order_status_history`, всегда в той же
транзакции, что и журналирование/применение события (шаги 13c/13e
§7). История — «статусы, в которых побывал заказ, с моментом
перехода **по данным маркетплейса**», а не временем получения
вебхука.

**Факты из снимка (FR-HIS-02).** Полный снимок сообщает не только
текущий, но и прошлые этапы заказа; из каждого **валидного** снимка
известного статуса выводятся все достоверно следующие факты:

| Факт | Момент `at` | Условие |
|---|---|---|
| `created` | `created_at` снимка | всегда |
| `paid` | `paid_at` | `paid_at ≠ null` |
| `cancelled` | `cancelled_at` | `cancelled_at ≠ null` |
| `shipped` / `delivered` | `updated_at` снимка | статус снимка — `shipped`/`delivered` (родного поля нет, T11) |
| факт текущего статуса `paid`/`cancelled` | родное поле, при null — `updated_at` (fallback FR-HIS-01) | статус снимка — `paid`/`cancelled` и факт ещё не выведен из родного поля |

Благодаря этому потеря/опоздание события не оставляет «дыр»:
например, первым пришёл `order.shipped` — факт `paid` восстановится
по `paid_at` этого снимка (S-07), а запоздавший `order.created`
дополнит историю фактом `created`, не меняя заказ (S-06).

**Откаты (FR-HIS-03).** Применённый снимок, **откатывающий** статус
(строгое убывание ранга `created=0 < paid=1 < shipped=2`), добавляет
факт коррекции `новый статус @ updated_at снимка` — момент ручного
исправления. Прогресс, повтор того же статуса и переход
в терминальный (`shipped → cancelled`) откатом не являются — факт
коррекции не создаётся. Переходы **из** терминальных статусов до
механики отката не доходят: они отклоняются раньше (13d, T-029),
отклонённый (`rejected`) снимок историю не меняет вовсе.

**Идемпотентность и stale (FR-HIS-02/04).** Вставка — пакетный
`INSERT IGNORE` по уникальному ключу `(order_id, status, at)`:
уже известный факт пропускается, отсутствующие вставляются,
обновлений существующих фактов нет — история только пополняется
(`source_event_id` — событие, из которого факт впервые следует).
Факты принимаются и из **устаревшего** снимка (`stale`): заказ
не меняется, но известные факты дополняются; факта отката при этом
нет — статус не меняется. Дубликаты и `ignored`-события историю
не трогают (применения нет).

**Порядок выдачи (FR-HIS-04).** Детерминированная сортировка —
`at ASC`, при равенстве — ранг статуса, затем `id` — выполняется
на уровне вывода (`OrderResource`, T-011); `at` хранится
в UTC (`DATETIME(0)`).

## Правила приёма событий

Кратко; полные формулировки — ТЗ §6.1–§6.2, схема данных и алгоритм —
[`architecture.md`](architecture.md).

### Разбор тела (T-021, шаги 5–11 §7)

Разбор выполняет `App\Support\MarketplaceEventParser` — единая точка
протокола тела, отдельно от бизнес-обработки (Action) и HTTP-слоя.
Ошибки **формата** (400, FR-WH-05) отличаются от ошибок **структуры**
(422, FR-WH-06/08) типизированной причиной `PayloadIssue`:

| Проверка по порядку | Отказ |
|---|---|
| тело — корректный JSON UTF-8 (не-JSON и битая кодировка неразличимы) | 400 `invalid_json` |
| `X-Webhook-Id` строго равен `body.id` (отсутствующий/не-строчный `body.id` совпасть не может) | 400 `event_id_mismatch` |
| базовый конверт: `id`/`type` — непустые строки; `created_at` — ISO 8601 дата-время **со смещением** (`±HH:MM` или `Z`; дробные секунды допустимы; несуществующие даты и offset вне диапазона — отказ); `data` — объект | 422 `invalid_envelope` |
| неизвестный `type` (не из шести `order.*`) — распознаётся здесь; формат `data.order` дальше **не проверяется** (T9: расширение протокола не должно вызывать бесполезные повторы) | — (→ 200 `ignored`, T-026) |
| известный тип: `data.order` — объект; `order.id` — непустая строка; `order.status` — строка (пустая — тоже: строкочное значение вне enum → `ignored`, не 422) | 422 `invalid_envelope` |
| строковый `order.status` вне enum | — (→ 200 `ignored`, T-026) |
| полный снимок известного статуса (FR-WH-08): `number`; `currency` — `^[A-Z]{3}$` без списка; `customer.{email,name}` — непустые строки, `phone` — string\|null; `items[]` — список `{sku,name,quantity≥1 (целое),price}`; суммы — строки `^-?\d+\.\d{2}$`; `shipment` — null либо `{carrier,tracking_number,tracking_url}`; `paid_at`/`cancelled_at` — null либо ISO 8601 со смещением; `cancel_reason` — string\|null; `created_at`/`updated_at` — ISO 8601 со смещением | 422 `invalid_snapshot` |

Невалидное тело не записывается в `webhook_events` (FR-ORD-08).
Порядок «структура → неизвестный статус» важен: не-строчный `status` —
это 422, а не «неизвестный статус → ignored» (S-17).

Формат email адреса при разборе **не** проверяется (только непустая
строка): невалидный адрес — причина пропуска письма `invalid_recipient`
(FR-MAIL-07), а не отказа вебхука.

### Арифметика total (FR-WH-09, S-27)

`total = Σ(price×quantity) + delivery − discount` — не основание для
отказа: снимок принимается, `total` хранится дословно как прислал
MarketHub. Расхождение логируется warning-ом с контекстом
`event_id`/`order_id`/`expected_total`/`declared_total` (A-17; стоимость
позиций — `Money::subtotal`, сложение и сравнение — `Brick\Math\BigDecimal`,
без float; T-022). Повторная доставка события
повторит запись warning-а — лог идемпотентен по смыслу, состояния нет.

### Общие правила

- **Идемпотентность по `event.id`** (FR-ORD-01): уникальный индекс
  `webhook_events.id`; повтор (в том числе параллельный и «после успеха»)
  → 200 `duplicate`, `deliveries++`, исходная запись не меняется
  (реализовано T-026 — детали и контракт altered-body в разделе
  «Журнал событий и идемпотентность»).
- **Версия заказа** (FR-ORD-02): кортеж
  `(order.updated_at, event.created_at, event.id)` UTC; входящий снимок
  применяется только при строго большей версии, иначе `stale`
  (реализовано T-028 — детали и контракт в разделе
  «Применение снимка заказа»).
- **Полная перезапись** (FR-ORD-04): снимок заменяет поля заказа и все
  позиции целиком, включая явные `null` (`shipment → null`, `paid_at → null`)
  (реализовано T-028).
- **Терминальные статусы** (FR-ORD-09, допущение Q35): из `delivered`/
  `cancelled` переходы в другой статус запрещены (включая
  `delivered ↔ cancelled`) → `rejected` с `reject_reason=
  terminal_status`; обновление при том же статусе разрешено
  (реализовано T-029 — детали и контракт в разделе «Применение
  снимка заказа»).
- **Неизвестный тип/статус** (FR-WH-07): событие сохраняется с исходом
  `ignored` (реализовано T-026), заказ/история/письма не меняются,
  ответ 200; `order_id` в журнале — из конверта (для неизвестного типа
  NULL, для неизвестного статуса — `data.order.id`).
- **История статусов** (FR-HIS-01…04): идемпотентные факты из каждого
  валидного снимка — применённого и устаревшего; откат фиксируется
  фактом коррекции; `rejected`/`duplicate`/`ignored` историю не меняют
  (реализовано T-030 — детали и контракт в разделе «История
  статусов»).

## Ручная отправка события

Готовый скрипт из материалов задания (подписует bytes файла как есть):

```bash
MARKETPLACE_WEBHOOK_SECRET=whsec_test_5f1d8c2a9b php task/examples/send-event.php \
    http://localhost/api/webhooks/marketplace task/examples/order-paid.json
```

Вручную через `openssl` (подпись считается от `"{timestamp}.{raw}"`; конвейер
`{ printf; cat; }` сохраняет финальный `\n` файла — command substitution
`$(cat …)` его бы срезала и подпись не сошлась):

```bash
ts=$(date +%s)
sig=$({ printf '%s.' "$ts"; cat task/examples/order-created.json; } \
    | openssl dgst -sha256 -hmac "whsec_test_5f1d8c2a9b" -hex | awk '{print $2}')

curl -sS -X POST http://localhost/api/webhooks/marketplace \
    -H 'Content-Type: application/json' \
    -H "X-Webhook-Id: $(jq -r .id task/examples/order-created.json)" \
    -H "X-Webhook-Timestamp: $ts" \
    -H "X-Webhook-Signature: sha256=$sig" \
    --data-binary @task/examples/order-created.json
```

> Скрипт `send-event.php` требует PHP с расширением curl на хосте.
> С T-024 подпись сверяется: невалидное тело отвечает 400/422 сразу.
> С T-026 исходы журналируются: неизвестный тип/статус отвечает
> 200 `ignored`, повтор того же `event.id` — 200 `duplicate`;
> с T-028 событие известного типа с валидным снимком применяется —
> 200 `processed` (или `stale` для устаревшей версии);
> с T-029 свежий снимок с другим статусом при заказе
> в `delivered`/`cancelled` отклоняется — 200 `rejected`;
> если лок `order:{id}` занят (например, из теста), тот же запрос
> отвечает 503 (T-027).
> Сквозной прогон по всем пяти примерам — сценарий приёмки S-35/§13.
